两个容易踩的细节

1. TCP 的序号按「字节」而不是按「包」

发送 1000 字节的段，下一段序号 = 上一段序号 + 1000。所以 ack 号表示「下一个期望字节」，而不是「第几个包」。这解释了大量「为什么 ack = seq + 长度」的题。

2. 窗口字段只有 16 位 → 窗口缩放选项

16 位最大 65535 字节，在高带宽时延积（BDP）链路上远远不够。窗口缩放选项（RFC 7323）把窗口扩大 2^shift 倍，shift 最大 14，因此窗口可达约 1 GB。

为什么是三次，而不是两次或四次？

两次不够

第二次握手之后，服务端无法确认「客户端收到了我的 SYN+ACK」。如果客户端没收到，它会重传 SYN，服务端会重复建立连接、浪费资源；反过来，旧的重复 SYN 也可能让服务端误开连接。

四次多余

服务端的 SYN 和 ACK 可以合并成一个报文发送，客户端同理。所以正常建立只需 3 次；四次挥手是因为 TCP 是全双工，两个方向要分别关闭。

本质

三次握手 = 双方各自确认「我的发送能力」和「你的接收能力」都被对方知晓，并同步初始序列号 ISN。两次只能单向确认。

为什么挥手要四次？TIME_WAIT 在等什么？

四次挥手

客户端发 FIN 只表示「我没有数据要发了」，此时它仍能接收；服务端先回 ACK（进入 CLOSE_WAIT，可能还有数据要发），等自己数据发完再发 FIN，最后客户端 ACK。因此 FIN 与 ACK 不能合并，共 4 次。

TIME_WAIT = 2 × MSL

主动关闭方在 TIME_WAIT 等 2MSL（Linux 默认 60 秒）。两个作用：① 让最后一个 ACK 有重传机会，防止服务端收不到 ACK 而反复重发 FIN；② 让本连接旧报文在网络中自然消亡，避免它们干扰使用相同四元组的新连接。

流量控制 vs 拥塞控制

同一件事的两个视角：rwnd 是接收方说「我还能收多少」，cwnd 是发送方猜「网络还能塞多少」。真正能发的窗口 = min(rwnd, cwnd)。

接收方缓冲区满时会通告 rwnd=0，发送方暂停并启动坚持定时器（persist timer）周期性探测窗口。

糊涂窗口综合征（SWS）：接收方每次只腾出几个字节就通告小窗口，导致发送方发大量低效小包。解决：接收方等窗口达到 min(MSS, 缓冲区/2) 再通告，发送方用 Nagle 合并小数据（但和延迟 ACK 一起可能带来 40–200ms 延迟，交互式场景用 TCP_NODELAY 关掉）。

丢包后：Tahoe 直接把 cwnd 打回 1；Reno 把 ssthresh 减半，cwnd 降到新 ssthresh（快速恢复），不必从头慢启动。

慢启动

cwnd 从 1 开始，每个 RTT 翻倍（指数增长），直到达到 ssthresh。

拥塞避免

越过 ssthresh 后每个 RTT 只加 1（线性增长），即 AIMD 中的「加性增」。

快速恢复

收到 3 个重复 ACK 判定单包丢失，ssthresh 减半、cwnd 减半，直接进入拥塞避免，而不是回到 1。

CUBIC 用三次函数让窗口在丢包后更快恢复（Linux 默认），BBR 则基于带宽和 RTT 建模而非丢包。它们都替代掉了 Reno 的 AIMD 增长方式，但「不压垮网络」的目标一致。

TCP：可靠但有队头阻塞

丢包被重传补上，数据最终完整且有序；但缺口之后所有数据都要等，应用层交付被整体推迟 —— 单连接内无法绕开。

UDP：不补，直接少一块

其余包照常按时到达，代价是永久丢失 + 可能乱序。适合「丢一块无所谓」的实时流，或者由应用自己决定要不要补。

QUIC：按流隔离

每条流独立重传，丢包只阻塞所在流；其他流继续交付。这就是 HTTP/3 在弱网下体验更好的核心原因之一。

Wireshark 里值得亲眼看的 5 件事

  • 窗口缩放：SYN 包里 WS= 值，后续所有窗口字段都要左移这个位数。
  • MSS 协商：SYN 选项里 MSS=1460，这是以太网 MTU 1500 减去 IP 20 + TCP 20。
  • 累计确认：连续多个段只回一个更大的 ACK；丢一个段时会出现一串相同 ACK。
  • 快速重传：3 个重复 ACK 后立刻看到同一个 seq 再次出现（时间上远小于 RTO）。
  • Nagle 与延迟 ACK：小包发送后要等 40–200ms 才被 ACK，交互式应用常因此变慢。

高频面试题（点击展开）

为什么 TCP 三次握手不是两次？
两次只能完成单向确认：服务端无法确认客户端收到了 SYN+ACK，也无法排除网络中旧的重复 SYN。三次才能让双方都确认「对方能收、自己能发」，并同步 ISN。
为什么挥手是四次，能优化成三次吗？
TCP 全双工，两个方向独立关闭。收到 FIN 只表示对方不再发数据，本端仍可能要发；ACK 与 FIN 通常不能合并，所以 4 次。若服务端也没有数据要发，可将 ACK 与 FIN 合并成 3 次（延迟确认/优化实现）。
TIME_WAIT 为什么是 2MSL？
① 若最后 ACK 丢失，服务端会重传 FIN，处于 TIME_WAIT 的客户端可以再回 ACK；② 让本连接残留报文在 2MSL 内消亡，避免污染同四元组的新连接。Linux 的 2MSL 实际为 60 秒。
大量 CLOSE_WAIT 说明什么？
被动关闭方收到了 FIN 但没有调用 close() 关闭 socket。通常是应用代码未正确释放连接（连接池泄漏、异常分支漏关），是 bug 而不是内核问题。
TCP 粘包是协议 bug 吗？
不是。TCP 是字节流，不保留消息边界，一次 recv 可能取到半个或多个应用消息。解决办法：固定长度、分隔符、或长度前缀（最常用）。UDP 保留边界，所以没有粘包问题。
为什么 UDP 没有拥塞控制会「害人」？
UDP 发送速率不受网络反馈约束，大量 UDP 流量会挤占带宽并造成丢包，波及同链路的 TCP。QUIC、RTP/RTCP、WebRTC 都在应用层实现了拥塞控制来避免这一点。
窗口 = min(rwnd, cwnd)，那 rwnd=0 会怎样？
发送方停发并启动坚持定时器，周期性发送 1 字节的窗口探测；接收方应用读取数据后发窗口更新（window update），发送方恢复。若窗口更新报文丢失，坚持定时器保证能探测到。
快速重传和超时重传的区别？
快速重传由 3 个重复 ACK 触发，不等 RTO，恢复更快；超时重传由 RTO 到期触发，代价大且会大幅降低 cwnd。现代协议还会用 SACK 精确告知缺哪段，避免重复传输已到达的数据。
