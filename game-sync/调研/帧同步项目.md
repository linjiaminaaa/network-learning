## 0. 一句话结论

**先读「服务器怎么组帧」再读「客户端怎么确定性重放」，最后才碰预测回滚；纯帧同步框架适合学模型，生产级游戏（OpenRA / OpenTTD / 0 A.D.）适合学 desync 排查。**

三条判断：

1. **教学性价比最高的是 CraneInForest 三件套**——它的 README 本身就是一篇中文帧同步长文（逻辑帧与渲染帧分离、定点数、随机数、服务器回放校验），且客户端/共享逻辑/服务器三层分仓，能直观看到「同一份逻辑代码在哪端跑」。
2. **只读一个回滚实现就选 GGPO**（`sync.cpp` / `input_queue.cpp` / `udp_proto.cpp` 三件套），现代替代看 GekkoNet（runahead、观战、desync detection 都有）。
3. **别拿 Unity 老 demo 直接当项目脚手架**：nibsbin/LockstepFramework、JiepengTan 系列、kisence 的 Unity 版本都已停更 5 年以上，能不能编译取决于你凑不凑得齐当年的 Unity/插件版本——它们的价值在读设计，不在跑。

#### 2.1.1 JiepengTan/Lockstep-Tutorial（1204 ★）

- **定位 / 解决什么**：中文帧同步教程仓库，分「阶段零 概要 → 阶段一 基础帧同步（第 1–6 节）→ 阶段二 预测回滚（第 7–15 节）」共 15 节编号内容，配套 B 站视频与博客。它不是一个库，而是一条学习路径 + 可运行示例。
- **同步模型归属**：阶段一=纯帧同步（输入广播 + 固定步长）；阶段二=预测回滚式帧同步（CSP + rollback，仍在帧同步范畴）。
- **精读位置**：根目录 `Unity/`、`Server/`、`CopySource/`、`RunClient/`、`RunServer/`、`RunServer1Client/`、`Server.sln`（2026-11-01 目录核对）。真正要读的是「阶段二」对应的预测/回滚代码，以及 `CopySource`（复制共享逻辑的机制）。
- **配套引擎**：教程底层用 [JiepengTan/LockstepEngine](https://github.com/JiepengTan/LockstepEngine)（967 ★，2020-03-23，未声明许可证），它聚合了确定性数学（LockstepMath）、确定性碰撞（LockstepCollision）、确定性寻路（LockstepPathFinding）、行为树（LockstepBehaviourTree）、序列化等多套确定性子库——国内 Unity 帧同步教程里常见的「全家桶」。
- **学习要点**：① 为什么教程要把「不同步的检测与定位」单列一节；② 预测缓冲区的自动伸缩；③ 多平台多实例下如何保证同一份逻辑；④ 教程明确「不含 ECS」，所以适合先建立同步模型再去看引擎。
- **坑与局限**：2019–2020 年的 Unity 工程，插件与资产（BEPU/Entitas 变体等）版本耦合严重；两个仓库都**无许可证声明**，代码只能读不能商用；README 有大量失效 B 站链接。
- **能否跑起来**：理论上用 Unity 打开 `Unity/` + 起 `Server.sln`；实际上不保证当前 Unity 版本兼容，建议只读代码。

#### 2.1.2 nibsbin/LockstepFramework（1540 ★）

- **定位 / 解决什么**：老牌 Lockstep Framework（LSF），面向 RTS / 塔防 / MOBA，自带确定性 2D 物理（X-Z 平面）、尺寸感知寻路、行为系统、数据库配置，以及 **lockstep variables**（能知道在哪一帧哪一处发生 desync）。它的社区分支 SnpM/LockstepFramework 被 proepkes/UnityLockstep 在 README 里明确致敬（"Inspired by LockstepFramework, in memory of SnpM"）。
- **同步模型归属**：确定性锁步（纯帧同步）；网络传输层可接 DarkRift 或 Photon。
- **精读位置**：根目录 `Core/`、`Database/`、`Example/`、`Integration/`、`Settings/`（2026-11-01 目录核对）；README 指定入口 `Example/ExampleScene`（Unity 场景）与 Ctrl+Shift+L 打开的 Lockstep Database 窗口；示例数据库 `Example/ExampleDatabase/Example_Database.asset`（均据 README）。
- **学习要点**：① 「lockstep variables」如何把 desync 定位到具体变量；② 自研确定性 2D 物理为什么比 PhysX 更适合锁步；③ 寻路把单位体积纳入考虑（大单位不卡窄口）；④ 数据库驱动配置，避免运行时随机初始化顺序。
- **坑与局限**：README 自述 **no longer actively developed**，最新提交针对 Unity 2019.1f1；GitHub 上满是 `.meta` 与子模块（`.gitmodules`、`Integration/` 依赖 DarkRift/Photon，需自行获取）；API 显示的 `pushed_at` 2026-05-23 与 README 的停更声明矛盾，**以 README 为准**。
- **能否跑起来**：需 Unity 2019.1f1 导入整个仓库，按 README 四步走（场景 → 数据库 → Load → Play）。老 Unity 授权/版本获取是主要门槛。

#### 2.1.3 proepkes/UnityLockstep（711 ★）

- **定位 / 解决什么**：确定性锁步 + 客户端预测 + 回滚的完整参考实现：ECS（Entitas）+ 定点数学（FixedMath.Net）+ 确定性物理（BEPUPhysics 的 int 定点分支 bepuphysics1int）+ LiteNetLib 服务器。它的价值在于**把「服务器权威组帧 + 客户端预测回滚」的分层直接摆给你看**。
- **同步模型归属**：帧同步为骨（fixed tick），客户端预测 + rollback 为肉（混合架构）。
- **精读位置**：根目录 `Docs/`、`Engine/`、`Server.LiteNetLib/`、`Unity/`（2026-11-01 目录核对）；`Docs/Overview.svg` 架构图（HTTP 200 验证）。README 的 Getting started 指路 `Server.LiteNetLib/Server.LiteNetLib.sln` 与 Unity `SampleScene`。
- **学习要点**：① 服务器只做「收输入 → 组帧 → 广播」，客户端负责仿真；② 回滚的生命周期（保存/恢复/重放）；③ 预测缓冲区与 rollback 触发条件；④ README 有一节 Limitations：物理值限制在 1000 以内，超出要平移世界坐标。
- **坑与局限**：README 的 WIP 列表很诚实——**帧率同步未解决**、**回滚上千 tick 是设计上的性能尖峰**、**被销毁实体的回滚尚未实现**；依赖 .NET Core 2.2.103 与 Entitas 1.13，属于「考古环境」。
- **能否跑起来**：按其步骤：起 `Server.LiteNetLib`（控制台，输入房间人数）→ Unity 里 Play → 右键持续生成 agent，按 X 让 agent 移动。环境凑齐可跑，但需要旧 SDK。

#### 2.1.4 kisence-mian/UnityLockStepDemo（1155 ★）

- **定位 / 解决什么**：Unity 帧同步 Demo，重点是**前后端统一语言**（客户端逻辑、服务端逻辑同一份 C# 代码）和「在框架层解决同步，写玩法不用管同步」。
- **同步模型归属**：帧同步（确定性锁步），服务端与客户端共享数据层逻辑。
- **精读位置**：据 README——客户端 `Script/SyncFrameWork`（前端同步框架）、`Script/SyncClientLogic`（表现层）、`Script/SyncGameLogic`（数据层，需与服务器一致）；服务器 `LockStepFrameWork`（帧同步框架）、`ServiceFrameWork`（C# 服务器框架）、`SyncGameLogic`、`Data`、`Network`、`Generate`；`App.config` 里的 `UpdateInterval`（帧更新间隔）与 `RoomPeopleNum`（房间人数）是理解「帧率即配置」的入口。
- **学习要点**：① 一份逻辑代码两端跑的目录约定；② 协议/数据表代码生成工具链（Tool_GenerateAnalysisCode 等）；③ 帧间隔可配置意味着逻辑帧与渲染帧解耦。
- **坑与局限**：README 自述「框架还在开发中」；依赖作者另一个私有仓库 MyUnityFrameWork 与 SuperSocket；无许可证；无法独立编译。
- **能否跑起来**：不建议，仅读目录设计与配置项。

#### 2.2.1 byebyebruce/lockstepserver（420 ★）

- **定位 / 解决什么**：Go 写的**脱离玩法逻辑**的帧同步房间服：KCP（kcp-go）+ protobuf，支持创建房间、读条同步、Ready 齐人开战、逐帧广播输入、断线重连补帧。目标就是「可横向扩展的纯帧同步服务器」。
- **同步模型归属**：纯帧同步；服务器只做输入汇合与帧广播，不做仿真。
- **精读位置**：根目录 `cmd/`、`logic/`、`pb/`、`pkg/`、`server/`（2026-11-01 目录核对）；`cmd/example_server/main.go`（部署入口）、`pb/message.proto`（消息定义，HTTP 200 验证）。README 给了完整消息流程（Connect → JoinRoom → Progress → Ready → Start → Input/Frame → Result）与 3 字节头（Body 长度 uint16 + MsgID uint8）的包格式。
- **学习要点**：① 「读条进度广播」为什么是帧同步开局的标配（等最慢玩家）；② 帧数据包如何压缩多个玩家的输入；③ 断线重连时「把历史帧分批补发」的朴素实现及它的优化空间（README 自己提示：可改成客户端请求缺失帧）；④ 服务器不跑逻辑 → 反作弊靠回放校验（见 2.2.2）。
- **坑与局限**：2022 年后停更；`travis-ci.org` 徽章已失效；断线重连的补帧实现是「全量分批」而非「按需补缺」，大房间/长对局会浪费带宽；没有房间匹配、没有鉴权，生产要自己补。
- **能否跑起来**：`go run cmd/example_server/main.go`；浏览器打开 `http://localhost` 建房间（或 `sh cmd/example_client/create_room.sh`）；两个客户端 `go run cmd/example_client/main.go -room=1 -id=1` / `-id=2`。Go 环境即可，**这是本文档里最快能跑起来的服务器**。

#### 2.2.2 CraneInForest/LockStepSimpleFramework 三件套（578 + 477 + 279 ★）

- **定位 / 解决什么**：Unity 帧同步「极简框架」+ 长篇中文实战文档 + 塔防 sample。用三个仓库把一件事讲透：**客户端跑表现、共享逻辑两端跑、服务器跑回放校验**。
  - [Client](https://github.com/CraneInForest/LockStepSimpleFramework-Client)（578 ★）
  - [Shared](https://github.com/CraneInForest/LockStepSimpleFramework-Shared)（477 ★，以 git submodule 形式同时挂到 Client 与 Server）
  - [Server](https://github.com/CraneInForest/LockStepSimpleFramework-Server)（279 ★）
- **同步模型归属**：帧同步 + 事后服务器校验（服务器不逐帧仿真，而是战斗结束后用同一份逻辑瞬间重放并比对结果，属混合）。
- **精读位置**：
  - 核心三文件（据 README）：`LockStepLogic.cs`（帧同步逻辑）、`Fix64.cs`（定点数）、`SRandom.cs`（可控随机数）。
  - `battle/` 下：`battle/core/action`（移动、延迟等基础事件）、`base`（战场对象基类）、`soldier`、`state`（状态机）、`tower`；另有 `ui`、`view`。
  - 服务器根目录 `Program.cs`（HTTP 200）与 `.gitmodules`（Shared 子模块）；客户端/共享仓库根目录各带 `README.md`。
- **学习要点**：① **逻辑帧 vs 渲染帧**：累计时间 while 循环追帧 + 渲染插值，README 直接给代码；② **禁用 float / Vector2 / Vector3**，用 `Fix64`/`FixVector2`/`FixVector3`，甚至连存 int 的 Vector2 都要换 `NormalVector2`（服务器不认 Unity 类型）；③ **可控随机数 + 战斗种子**；④ **`_CLIENTLOGIC_` 宏**把渲染代码在服务器端编译掉；⑤ 服务器校验只比「逻辑帧数 + 业务指标」——因为哪怕一丁点不一致，帧数就跑不齐。
- **坑与局限**：客户端 unity5.5.6f1、服务器 fedora27 + mono（`mono LockStepFrameWork-server.exe`），2018 年的环境；**必须先 `git submodule update --init --recursive`**，否则共享逻辑缺失编译不过；README 提到工程目录里有 `.git`/`.gitmodules` 会导致 MonoDevelop 崩溃，需临时删掉；服务器只是「极简 socket + 回放校验」（端口 2333），不是完整战斗服。
- **能否跑起来**：能跑，但环境是考古级：Unity 5.5.6f1 打开 Client → 起 Server（mono）→ 打一场 → 回放校验。若只想读，README 本身已值回票价。

#### 2.2.3 wqaetly/NKGMobaBasedOnET（1013 ★）

- **定位 / 解决什么**：基于 ET 框架的类 LoL MOBA 全栈 Demo，主打**状态帧同步**（state frame sync）+ **完整预测回滚**，并带双端行为树技能系统、FGUI、ILRuntime 热更、xasset 资源热更、recastnavigation 寻路、KCP 网络。它是理解「状态同步与帧同步可以混着来」的最佳对照案例。
- **同步模型归属**：混合——以帧为驱动单位广播**状态/行为**，客户端预测 + 回滚。
- **精读位置**：根目录 `Server/`、`Unity/`、`Proto/`、`Config/`、`Excel/`、`ThirdParty/`、`Server.sln`（2026-11-01 目录核对）。README 指明网络算法用 KCP、预测回滚参照「守望先锋 GDC2017 分享」（附中文翻译系列博客与 B 站教程合集）。
- **学习要点**：① 状态帧同步与纯输入帧同步的区别（前者把状态/行为也纳入帧内容）；② 预测回滚在 MOBA 技能这种「非纯物理」场景怎么落地；③ 双端行为树（客户端表现 + 服务器判定）怎么保证一致；④ 热更新/资源更新对同步的干扰。
- **坑与局限**：体量巨大且依赖一堆 **Asset Store 付费插件**（ParadoxNotion-Slate、Odin、Animancer、MonKey Commander、Status Indicators，README 明示「仅供学习交流使用，请支持正版」）；需 Unity 2020.3.12 LTS + .NET Core 3.1；Wiki 在 gitee；停更于 2022。**环境基本不可能凑齐，只适合读架构 + 看配套博客**。
- **能否跑起来**：不建议；把 README 当目录，配合作者的系列博客读 `Server/` 的帧同步与回滚部分。

### 2.3 ③ 确定性基础设施（定点数 / 确定性物理 / 确定性随机）

#### 2.3.1 Kimbatt/unity-deterministic-physics（556 ★）

- **定位 / 解决什么**：把 Unity DOTS Physics 0.6.0-preview.3 改写为**跨平台确定性物理**：核心手段是用 soft float（软件模拟浮点）替换硬件浮点，从而消除不同 CPU/编译器的浮点差异。命名空间改成 `UnityS.Physics` / `UnityS.Mathematics` 以区别原版。
- **同步模型归属**：确定性基础设施（服务于帧同步的物理层）。
- **精读位置**：根目录 `Assets/`、`Packages/`、`ProjectSettings/`（2026-11-01 目录核对）；README 的「Notes on determinism」六条是全文精华；示例场景为 `ExampleScene`（据 README）。
- **学习要点**：README 直接列出破坏确定性的写法，比读代码更值：① 所有 body 必须**按相同顺序**创建；② 只在 `FixedStepSimulationSystemGroup` 更新的 system 里改 body；③ **不要把浮点运算结果喂给物理引擎**；④ HashMap/HashSet 迭代顺序不确定（取决于实现）；⑤ soft float 的用法；⑥ 业务代码自身也必须确定性。
- **坑与局限**：基于 DOTS Physics **0.6 preview**（Unity 早已升级/废弃该版本），依赖 Burst/Collections/Entities/Jobs 的旧版；soft float 性能显著低于硬件浮点；仓库无自有 LICENSE（受 Unity Companion License 与 MIT 双重约束，商用前必须核对）；last push 2024-02。
- **能否跑起来**：需要凑齐旧版包组合，基本不可行；把它当「确定性物理的检查清单」读。

#### 2.3.2 mrdav30/FixedMathSharp（95 ★）

- **定位 / 解决什么**：为 .NET 提供**完整 Q32.32 定点数值栈**：`Fixed64` 标量、向量/矩阵/四元数、变换、曲线、包围体、射线、三角形，以及**确定性随机流**；可选 MemoryPack 序列化。定位就是「不绑引擎的确定性数学底座」，用于 lockstep 仿真、可复现生成、回放。
- **同步模型归属**：确定性基础设施。
- **精读位置**：`docs/MIGRATION.md`（定点语义/破坏性变更的说明，HTTP 200 验证）、`tests/FixedMathSharp.Benchmarks/README.md`（性能基准的「证据规则」，HTTP 200 验证）、`LICENSE`；核心 `Fixed64` 实现在仓库 `src/` 下（具体文件路径未核实）。另有 Unity 适配包 [FixedMathSharp-Unity](https://github.com/mrdav30/FixedMathSharp-Unity)。
- **学习要点**：① Q32.32 的取值/精度/溢出语义（README 强调「documented rounding and overflow behavior」）；② 「全定义域中间运算」避免过早饱和（这是定点数学最容易翻车的地方）；③ 只在渲染/编辑器边界转 float/double；④ 确定性随机流怎么和定点数配套；⑤ 有 BenchmarkDotNet 基准与覆盖率，看它怎么写「性能证据」。
- **坑与局限**：只覆盖 .NET（Unity 需另装适配包）；95 ★、单人维护，长期支持看运气；Q32.32 的数值范围（约 ±2^31）对超大地图/超长时间累积需要自己缩放；`src/` 具体文件名未核实，按 NuGet 包或 clone 后看。
- **能否跑起来**：`dotnet add package FixedMathSharp` 即可；仓库自带测试与基准，`dotnet test` / 基准项目可跑。**这是本类里唯一「今天就能上手」的项目**。

> 补充（未展开成小节，但已核实存在）：[JiepengTan/Lockstep.Math](https://github.com/JiepengTan/Lockstep.Math)（73 ★，C#，2023-01-02，无许可证）是 LockstepEngine 的定点数学子库；[PetteriAimonen/libfixmath](https://github.com/PetteriAimonen/libfixmath)（889 ★，C，2026-10-30，GitHub 未识别许可证但 README 写 MIT）是 Q16.16 的经典 C 实现，适合快速理解定点格式取舍，但**不再积极维护**（README 自述只收 PR）。

### 2.4 ④ 回滚网络（GGPO 系 / rollback netcode）

| 项目 | 语言 | ★（2026-11-01） | 最近提交 | 许可证 | 定位 | 能否跑 |
|---|---|---|---|---|---|---|

| [HeatXD/GekkoNet](https://github.com/HeatXD/GekkoNet) | C++ | 64 | 2026-10-24 | BSD-2-Clause | 现代 C/C++ 回滚 SDK（GGPO/GGRS 思路重构） | 能（CMake + C++20） |

#### 2.4.1 pond3r/ggpo（3617 ★）

- **定位 / 解决什么**：把「输入预测 + 投机执行 + 回滚重放」做成 SDK：不等远端输入，先按猜测跑，收到真实输入若与猜测不符就**回滚到快照并重放**，从而让玩家感觉「零延迟」。附带 `vectorwar` 示例程序（2~4 人）。
- **同步模型归属**：回滚网络（rollback netcode），本质是「带状态快照/恢复的确定性仿真」。
- **精读位置**（均已 HTTP 200 验证）：`src/lib/ggpo/sync.cpp`（回滚与状态管理核心）、`input_queue.cpp`（输入预测/确认队列）、`network/udp_proto.cpp`（UDP 协议与输入冗余）、`backends/p2p.cpp`（P2P 会话与确认帧协商）、`src/include/ggponet.h`（对外 API）、`src/apps/vectorwar/vectorwar.cpp`（示例）。
- **学习要点**：① 回滚的前提是**状态可保存/可恢复**——SDK 只定义接口，`save_game_state` / `load_game_state` 要游戏自己实现（这是最大工作量）；② 输入包怎么冗余发送（同一输入带前几帧，抗丢包）；③ 确认帧（confirmed frame）如何推进、何时停止回滚；④ 时间同步（timesync）与帧延迟调节。
- **坑与局限**：README 明说**目前只在 Windows 上可构建**（VS2019 + CMake）；C++/回调式 API，接引擎成本高；此仓库更新缓慢（last push 2024-06）；无观战/无 runahead/无 desync detection（这些要自己做）。
- **能否跑起来**：`build_windows.cmd` 生成 `build/GGPO.sln` → VS2019 编译 → `vectorwar.exe <localport> <num players> ('local' | <remote ip>:<remote port>) ...`；`bin/` 下自带 2/3/4 人启动脚本。**Windows 上最快能跑的回滚 demo**。

#### 2.4.2 HeatXD/GekkoNet（64 ★）

- **定位 / 解决什么**：作者嫌 GGPO 回调式 API 难用、又不想受 Rust FFI 折磨，于是写了原生 C/C++ 的现代回滚 SDK（思路来自 GGPO 的 Rust 重实现 GGRS）。功能比 GGPO 新：runahead（本地抢跑隐藏输入延迟）、观战（可中途加入、落后追帧）、回放（带每帧 checksum，回放时能报出第一个不一致帧）、desync detection、断线处理、压力测试会话。
- **同步模型归属**：回滚网络（GGPO 系）。
- **精读位置**：根目录 `GekkoLib/`（核心库，CMake 工程，`GekkoLib/CMakeLists.txt` 已验证）、`Examples/`（示例，需 SDL3）、`docs/`（文档与图片）、`GekkoNet.sln`（2026-11-01 目录核对）。README 的功能清单（Done / Maybe Later）就是最好的阅读路线图。
- **学习要点**：① runahead 与输入延迟的取舍；② 观战者如何「从确认状态加载再续跑」；③ **回放 checksum 找第一处 desync** 的设计（生产环境极实用）；④ 「stress session」——本地反复回滚来主动找不同步，这个思路值得抄；⑤ 抽象 socket manager 便于换传输层。
- **坑与局限**：64 ★、单人项目，API 还在演进；examples 需要 SDL3 和较新的 VS（README 写 Visual Studio 2026）；文档在 GitHub Pages，仓库内代码注释密度一般；不如 GGPO 生态成熟（没有现成引擎插件）。
- **能否跑起来**：`cmake -S GekkoLib -B build && cmake --build build`，产物在 `out/`；示例另需 SDL3。

#### 2.5.1 OpenRA/OpenRA（17702 ★）

- **定位 / 解决什么**：西木经典 RTS（红警、泰伯利亚黎明、沙丘 2000）的开源重制引擎。默认分支是 `bleed`（README 内链接均指向 bleed），多人联机靠确定性锁步。**它是「工业级帧同步 + desync 排查」的活教材**，而且还在活跃开发。
- **同步模型归属**：确定性锁步帧同步；客户端之间只传玩家指令（订单），各端本地仿真。
- **精读位置**（均已 HTTP 200 验证）：
  - `OpenRA.Game/Network/OrderManager.cs` —— 订单队列、帧号推进、延迟补偿的核心
  - `OpenRA.Game/Network/Order.cs` —— 订单的数据结构（指令如何序列化）
  - `OpenRA.Game/Network/SyncReport.cs` —— **desync 检测**：定期比对哈希、生成同步报告（含玩家、帧号、差异项）
  - `OpenRA.Game/Network/Connection.cs` —— 连接/握手/延迟测量
  - `OpenRA.Game/Network/ReplayConnection.cs` —— 回放即「重放订单流」
  - `OpenRA.Game/Game.cs`、`OpenRA.Game/World.cs` —— 主循环与仿真世界
- **学习要点**：① 订单（Order）粒度的同步：不是同步单位位置，而是同步「下达了什么命令」；② 哈希比对 + 同步报告的工程化写法（能定位到具体 trait/字段）；③ 回放复用同一套订单流，不存录像文件的位置信息；④ 观战/加入中局的处理；⑤ 用整数/定点化的世界坐标规避浮点（在其坐标类型里体现，具体文件未逐条核实）。
- **坑与局限**：代码量巨大（引擎 + 多个 mod 的 C#），不是教学仓库；多人 desync 报告需要读懂官方 wiki；构建需要对应 .NET SDK（见 `INSTALL.md`）；Mod 内容与引擎耦合。
- **能否跑起来**：官网下载发行版直接玩（最快）；或按 `INSTALL.md` 用 .NET SDK 编译；专用服务器见 wiki 的 Dedicated Server 页。

#### 2.5.2 OpenTTD/OpenTTD（8445 ★）

- **定位 / 解决什么**：运输大亨开源重制，二十多年历史，多人联机是**命令队列 + 固定 tick 的确定性锁步**。最值得学的是它**对 desync 的工程化处理**：官方专门维护 `docs/debugging_desyncs.md` 教人抓 desync dump。
- **同步模型归属**：确定性锁步帧同步（命令/事件在 tick 边界按固定顺序执行）。
- **精读位置**（均已 HTTP 200 验证）：

  - `src/network/network_command.cpp` —— **命令的排队、分发与同步**（锁步的核心）

  - `src/network/core/tcp_game.h` —— 游戏连接的包类型定义

- **学习要点**：① 为什么命令要在固定 tick 执行、按 `ClientID` 排序；② 客户端命令的「本地先行」与服务器确认之间的关系；③ desync dump 里看什么（随机种子、命令序列、GRF 版本）；④ 版本/存档兼容性策略。
- **坑与局限**：巨型 C++ 代码库（20 年积累），编译需要图形/音频依赖；README 强调需要额外图形音效数据文件（OpenGFX/OpenSFX）才能运行；许可证三层（主 GPLv2 + 3rdparty 各自许可），引用代码要看清。

## 3. 三条路线对比表

| 维度 | ① 纯帧同步框架/引擎 | ② 锁步游戏服务器 | ③ 确定性基础设施 |
|---|---|---|---|
| 代表项目 | Lockstep-Tutorial、nibsbin/LSF、proepkes/UnityLockstep | byebyebruce/lockstepserver、CraneInForest 三件套、NKGMoba | FixedMathSharp、Kimbatt 确定性物理 |
| 解决的核心问题 | 客户端本地怎么跑出「同一帧同一结果」 | 多端输入怎么汇合、怎么组帧、怎么补帧 | 数学/物理层怎么保证「同输入同输出」 |
| 确定性责任 | 框架 + 游戏逻辑（要自己写对） | 一般在客户端（服务器只组帧）或回放校验 | 库保证（但用法错照样崩） |
| 网络模型 | P2P 或 服务器中继 | 房间服 / 战斗服 / 回放校验服 | 无网络，纯本地 |
| 学习曲线 | 中（要先懂 ECS/Unity） | 低-中（建议从这里入门） | 低（但坑最深：溢出/舍入/遍历顺序） |
| 上手成本 | 高（Unity 老版本、插件） | 低（Go/C# 即可跑） | 低（NuGet/CMake） |
| 适合谁 | 要自研引擎/框架的人 | 要接服务器/房间系统的人 | 要保证跨平台一致的人 |
| 主要坑 | 环境考古、许可证缺失 | 断线补帧、反作弊、读条同步 | 浮点混入、遍历顺序、性能 |
| 典型误区 | 以为「有库=有确定性」 | 以为「服务器跑逻辑=不用回放校验」 | 以为「用定点数就万事大吉」 |

## 附录 B：数据来源与核实方法

1. **元数据（★ / 语言 / 许可证 / 最近提交 / default_branch / archived）**：GitHub REST API 2026-11-01 返回值。本次共调用 **14 次**（4 次 search + 9 次单仓库 `/repos` + 1 次 `/contents`），控制在团队约定的 15 次以内；JSON 先落盘再解析，未重复请求。
2. **描述与运行方式**：`raw.githubusercontent.com` 的 README（`master`/`main` 都试过），2026-11-01 抓取；引用时以「据 README」标注未逐行验证的内容。
3. **「精读位置」真实性**：对每个标注的文件/目录做两种核对之一——
   - `raw.githubusercontent.com` 直接探测返回 HTTP 200（如 OpenRA `OrderManager.cs`、OpenTTD `network_command.cpp`、GGPO `sync.cpp`、0 A.D. `TurnManager.cpp`）；
   - 抓取仓库根目录页面内嵌 JSON 得到一级目录清单（如 `CraneInForest-Server` 的 `battle/`、`GekkoNet` 的 `GekkoLib/`）。
   未能探测到的路径一律标「未核实」或「据 README」，不臆造。
4. **许可证提醒**：`license=null` 表示仓库未声明许可证（默认「保留所有权利」），**不可直接商用/复制代码**；0 A.D.、OpenTTD、libfixmath 的 GitHub SPDX 字段与实际许可证不一致，已按仓库内 README/LICENSE 文件修正并注明。
