## 0. 一句话结论

状态同步的**骨架只有四件事：服务器权威模拟 → 快照/delta 编码 → 不可靠 UDP 传输 → 客户端预测 + 插值校正**；想少走弯路就按「Gambetta 四篇文章 → 一个 200 行级的教学实现 → 一个生产级框架的同步层源码 → 一个传输层」的顺序读，**不要**从 skynet / ET 这种万行级框架入门。

## 2. 状态同步技术栈分层图

```
┌─ 表现层 Presentation ────────────────────────────────────────────────────────┐
│ 插值 / 外推 / 误差平滑 / 回滚渲染 / 动画混合                                   │
│ 代表：snapshot-interpolation · godot-state-sync-demo                           │
├─ 同步层 Replication ─────────────────────────────────────────────────────────┤
│ 快照生成 · 变化集(delta) · 位打包 · 量化 · 可见性/AOI                          │
│ 代表：colyseus/schema · bevy_replicon · PurrNet BitPacker                      │
├─ 权威层 Authority ───────────────────────────────────────────────────────────┤
│ 房间/匹配 · 固定 tick · 输入校验 · 预测校正 · 反作弊                           │
│ 代表：colyseus · nakama · chickynoid · unity-fastpacedmultiplayer              │
├─ 传输层 Transport ───────────────────────────────────────────────────────────┤
│ 可靠/不可靠 UDP · 分片重组 · ack · 拥塞 · 加密 · 握手                          │
│ 代表：GameNetworkingSockets · LiteNetLib · yojimbo · netcode                   │
└──────────────────────────────────────────────────────────────────────────────┘

        ▲ 上行：输入命令 + tick 序号              ▼ 下行：快照 + 事件
```

| 层 | 一句话职责 | 关键问题 | 本榜单代表项目 | 建议先读 |
|---|---|---|---|---|
| 传输层 | 把「一帧字节」靠 UDP 送出去 | 丢包/乱序/抖动/MTU/加密 | GameNetworkingSockets、LiteNetLib、yojimbo | GNS 的 `SNP_WIRE_FORMAT.md` |
| 权威层 | 只有服务器说了算 | tick 频率、输入校验、预测与校正、重连 | colyseus、nakama、chickynoid、unity-fastpacedmultiplayer | `AuthCharPredictor.cs` |
| 同步层 | 决定「发什么、发多少」 | 全量还是 delta、量化精度、位打包、AOI | colyseus/schema、bevy_replicon、PurrNet、NGC | `src/Schema.ts` |
| 表现层 | 让 20Hz 的状态看起来像 144Hz | 插值缓冲、外推上限、误差平滑 | snapshot-interpolation、godot-state-sync-demo | `src/vault.ts` |

**一次典型的服务器权威同步（8 步）**

1. **输入上行**：客户端把本帧输入（移动向量/按键）打包，附上「我预测的第 N tick 状态」发给服务器。
2. **服务器模拟**：服务器在自己的固定 tick（如 33ms）里跑权威模拟，输入先校验（反作弊）再施加。
3. **生成快照**：把本 tick 的世界状态整理成快照（全量或只标脏字段）。
4. **编码压缩**：schema/delta → 位打包 → 量化（位置 float32 → 定点 16bit 之类）。
5. **下行传输**：走不可靠通道（丢了等下一帧，不同步重传）+ 可靠通道（开箱、命中这类关键事件）。
6. **客户端收包**：按 tick 序号放入抖动缓冲（jitter buffer），丢弃过期快照。
7. **校正**：比对「本地预测状态」与「服务器快照」，小误差平滑吃掉，大误差直接回滚重放（rollback）。
8. **表现**：在相邻两帧快照之间插值 + 外推补网络延迟，渲染帧率与 tick 率解耦。

#### 3.1 colyseus/colyseus — 带 schema 状态同步的房间服（Node.js）

| 项 | 值 |
|---|---|
| 仓库 | <https://github.com/colyseus/colyseus> |
| 语言 / Stars | TypeScript / **7,499** |
| 最近提交 | **2026-11-01 05:17**（默认分支 `master`） |
| 许可证 | MIT |
| 同步模型 | **状态同步**（房间 + schema 增量广播），仓库内另有 `PREDICTION.md` 讨论客户端预测 |

**解决什么问题**：把「房间生命周期 + 匹配 + 状态同步 + 客户端 SDK」打包成开箱即用的房间服。你定义 `Room` 类和 `Schema` 状态类，框架负责 tick、序列化变化字段、广播给房间内客户端。

**精读位置**（均在 `master`）
- `packages/core/src/Room.ts` — 房间生命周期、`setState`/`onMessage`、每 tick 的状态 patch 广播。**先读这个文件**。
- `packages/core/src/Protocol.ts` — 握手与消息编号（客户端/服务端协议表）。
- `packages/core/src/RoomMessages.ts` — 房间消息类型定义。
- `packages/core/src/MatchMaker.ts` — 房间创建/加入/座位分配。
- `packages/core/src/Rewind.ts` — 回滚相关（配合 `PREDICTION.md`）。
- `packages/core/src/Transport.ts` — 传输抽象（WebSocket / uWebSockets 可换）。
- `PREDICTION.md` — 作者对「在这套房间模型上做客户端预测」的说明，必读。

**学习要点**
1. 「状态定义 → 自动增量」的工程解耦：业务只改对象属性，框架比对出变化字段。
2. 房间 = 权威边界：一个 Room 内状态一致，跨 Room 不共享，这是最省心的分片方式。
3. 协议分层：握手 → 房间加入 → 状态 patch → 消息，读 `Protocol.ts` 可画出完整时序。

**坑与局限**
- Node.js/TS 生态，性能上限受单进程（可用多进程 + Redis 扩展，但复杂度上升）。
- 状态同步强绑定 `@colyseus/schema`（见 3.3），换序列化方案等于换框架。
- 官方文档质量高，但核心代码含大量「历史兼容 + 多传输」分支，第一遍读要跳过非核心目录。

**能否跑起来**：README 给出的客户端安装命令是 `npm install @colyseus/sdk`（TypeScript）/ `npm install @colyseus/react`；**服务端安装与启动命令 README 未直接给出**（指向官方 docs），此处不编造。可直接跑现成示例仓库 `colyseus/colyseus-examples`（197★，MIT，2026-02-07 提交）。

### ② 快照 + 增量序列化（schema / 位打包 / 量化 / delta）

#### 3.3 colyseus/schema — 自动状态复制的 schema 库（字段级 delta）

| 项 | 值 |
|---|---|
| 仓库 | <https://github.com/colyseus/schema> |
| 语言 / Stars | TypeScript / **173** |
| 最近提交 | **2026-10-29 23:21**（`master`） |
| 许可证 | MIT |
| 同步模型 | **状态同步**：schema 反射 + 只发送变化的字段（change tracking） |

**解决什么问题**：给服务端状态对象加 schema 描述，运行时自动追踪「哪些字段变了」，客户端按同一份 schema 反序列化增量。是 3.1 的同步引擎，也可单独用于别的游戏服。

**精读位置**
- `src/Schema.ts` — 状态基类、字段变更回调、`onChange` 钩子。
- `src/Reflection.ts` — 反射：从 TS 装饰器/类型信息建 schema 元数据。
- `src/Metadata.ts` — 字段元数据（类型、索引、默认值）。
- `src/annotations.ts` — 装饰器定义。
- `src/codegen/languages/csharp.ts`、`cpp.ts`、`gdscript.ts`、`dart.ts` — **多语言代码生成**，理解"同一份状态定义跨客户端语言复用"。

**学习要点**
1. **字段级 delta 的代价与收益**：省带宽，但需要维护"每客户端可见状态基线"，掉线重连要发全量基线。
2. 反射 + 代码生成的组合：服务端用反射拿元数据，客户端用生成代码反序列化，避免运行时反射开销。
3. 结合下文 `schema-codegen` 命令，看一个 `State.ts` 如何变成 C#/C++ 客户端类。

**坑与局限**
- star 数不高（173），但它是「schema 自动增量」这一路线的代表作，别用 star 数判断价值。
- 不是位打包（bit-packing），是变长编码的字段 delta；追求极致带宽要看 3.8 PurrNet BitPacker 或 yojimbo。
- v3 重写后 API 有变化，网上旧教程（v2）会对不上。

**能否跑起来**：README 提供代码生成命令，例如 `schema-codegen ./schemas/State.ts --output ./unity-project/ --csharp`（要求项目有 TypeScript 5.x/6.x）。作为库被 3.1 使用，独立运行意义不大。

**学习要点**
1. 脏标记 → 批量发送的典型实现：默认每 tick 只发变化的变量，带"变化时间点"。
2. **它没有真正意义上的客户端预测/回滚**——官方把预测能力放在 Netcode for Entities（DOTS）方向；所以别把这个仓库当预测教材。
3. 读 ILPP 文件能理解为什么 Unity 的"注释即配置"能生效。

**坑与局限**
- **UCL 许可证**：只能用于 Unity 相关项目，不是自由软件，代码引用要遵守条款。
- 默认分支是 `develop-3.x.x`（不是 master/main），看代码注意版本。
- 大数据量/高频率场景（MMO、车枪球）性能一般，社区普遍迁移到 Netcode for Entities。
- RPC 与 NetworkVariable 语义常被混用导致 bug（延迟/顺序问题），官方文档有专门章节。

**能否跑起来**：作为 Unity Package 使用（README 指向官方手册与 Discord）；仓库内有 `Examples/DocumentationExamples/` 可参考，但需要 Unity 编辑器环境，无命令行 demo。

- `example_backend/examples/simple_button.rs` / `authoritative_rts.rs` — 两个可跑示例（含一行启动命令）。

**学习要点**
1. **"复制规则"取代手写同步代码**：与 3.4 NGC 的 `[NetworkVariable]` 是同一思路的两种表达。
2. 变更检测（change detection）驱动 diff，是 ECS 天然优势。
3. 无内建 IO 的设计哲学：同步层与传输层彻底解耦（对照 3.10）。

**坑与局限**
- 需要 Rust + Bevy 基础；Bevy 版本升级快，crate 版本要对齐。
- **不能"直接跑"**：示例依赖 `example_backend` 的 TCP 后端（README 明确说不要用于生产）。
- 文档在 docs.rs，仓库 README 只是概览。

**能否跑起来**：`example_backend/README.md` 原文：`cargo run -p bevy_replicon_example_backend --example <example name> -- <example CLI args>`；先起服务器再起客户端（示例用阻塞式 TCP）。

#### 3.14 PurrNet/PurrNet — 现代 Unity netcode（bit-packer + delta）

| 项 | 值 |
|---|---|
| 仓库 | <https://github.com/PurrNet/PurrNet> |
| 语言 / Stars | C# / **703** |
| 最近提交 | **2026-10-29 19:11**（默认分支 `dev`） |
| 许可证 | MIT |
| 同步模型 | **状态同步**：bit-packing + delta 压缩的 SyncVar + 预测 + 多传输后端（UDP / WebTransport / UTP / Steam / Nakama） |

**解决什么问题**：想比 Unity 官方 NGC 更省带宽、更可控：自带 bit-packer、压缩类型（CompressedFloat/CompressedVector2）、代码生成的 delta 序列化器，传输层可插拔。

**精读位置**
- `Assets/PurrNet/Runtime/BitPacker/BitPacker.cs` — 位打包核心。
- `Assets/PurrNet/Runtime/BitPacker/Delta/CompressedFloat.cs`、`CompressedVector2.cs` — **量化压缩的现成实现**（float → 定点）。
- `Assets/PurrNet/Codegen/GenerateDeltaSerializersProcessor.cs` — 编译期生成 delta 序列化器。
- `Assets/PurrNet/Runtime/Transports/UDPTransport.cs`、`CompositeTransport.cs` — 传输层抽象与组合。
- `Assets/PurrNet/Runtime/Transports/Interface/ITransport.cs` — 传输接口，理解"可插拔"设计。
- `Assets/Examples/` — 顶视角射击等示例。

**学习要点**
1. **量化是带宽的第一杠杆**：位置 3 个 float32 = 12 字节，量化成 3×16bit = 6 字节，肉眼几乎无差。
2. 代码生成（Codegen）把反射开销移到编译期——与 colyseus/schema 的 codegen 思路一致。
3. 多传输后端对照表可以看出"同步层应该只依赖什么接口"。

**坑与局限**
- 默认分支是 `dev`（不是 main/master），API 变动频繁；Unity 2022+。
- 社区/文档规模比 FishNet 小；部分高级功能可能在资产商店版本。
- 强 Unity 绑定。

**能否跑起来**：README 原文：`openupm add dev.purrnet.purrnet`（或用 Unity Package Manager 加 git URL）；`Assets/Examples/` 有示例场景。
