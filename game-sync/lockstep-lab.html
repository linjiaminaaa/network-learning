两条路线，一场 3 人战斗

同一场 3 人战斗，用两条同轴时间线并排看：帧同步让每个客户端各自跑逻辑，服务器只转发「谁按了什么」；状态同步让服务器算完再广播「世界长什么样」。拖动时间轴或点播放，跟着每一跳消息走一遍，再往下逐个拆开。

参数固定为：10 Hz 逻辑帧（每帧 100 ms）、3 个客户端（A 单向 55 ms / B 75 ms / C 145 ms）。拖动上方滑块可以暂停并逐帧观察；两条时间线共用同一根时间尺，方便对齐比较。

帧同步：传「指令」

客户端各自模拟。服务器只做两件事：收齐同一帧所有玩家的输入、把这一帧的完整输入集合广播出去。三端算出相同状态，带宽与实体数无关。

客户端 边算边传输入 → 服务器 凑齐再广播 → 三端 各自执行
状态一致靠：确定性 + 同样的输入集合

状态同步：传「结果」

服务器是唯一权威：跑逻辑、出快照，客户端只负责发输入与渲染。快照丢了没关系，下一份覆盖；但带宽随实体数增长，客户端看到的世界总是「过去时」。

客户端 发输入 → 服务器 模拟+快照 → 客户端 渲染快照
一致靠：服务器权威 + 快照覆盖
你现在看到的是：两条路线在时间线上的骨架 —— 帧同步是「输入上行 + 帧确认下行，最慢者拖住全房间」，状态同步是「输入上行 + 快照下行，每个人看到的都是服务器的旧画面」。接下来逐个模块拆机制。

帧同步流水线：最慢的人决定所有人

一帧的完整流程是「采集输入 → 上行 → 服务器归并 → 凑齐后广播 → 各端执行」。UDP 会丢包，而帧同步不能丢输入，所以每个输入包都携带最近 3 帧的冗余输入；只要有一个玩家的输入没到齐，整房间就停在这一帧 —— 这叫等帧卡顿。

追帧与断线重连：全量快照 + 输入回放

帧同步客户端掉线后错过了 N 帧输入，不能「凭空重算」。服务器先下发一份全量快照（完整实体状态 + 随机数状态 + 种子 + 计时器），再补发缺失帧的输入集合；客户端从快照帧开始跑，一边以数倍速重放追赶，一边等实时网络恢复。追帧期间通常禁用渲染插值。

全量快照大小 = 头部 8 B + 实体数 × 16 B；本场景 300 实体 ≈ 4.8 KB（一次性）
追上所需真实时间 ≈ 落后帧数 / ((追帧倍速 − 1) × 60) 秒。倍速越高越容易引起掉帧，工程上要设预算上限（如每帧最多追 8 帧）。

点「重连并追帧」：服务器先发快照，客户端从快照帧开始以倍速重放，逐步缩小与实时帧的差距。

你现在看到的是：追帧不是「快进画面」，而是连续执行已知帧的 step()、不渲染中间帧。倍速越高追得越快，但单帧时间预算有限；真实实现通常限制每帧追帧数，先保证「不再落后」，再慢慢追平。

状态同步：权威快照 + 预测 / 校正 / 插值

服务器以 20 Hz 跑权威逻辑，每 50 ms 广播一次快照；客户端只发输入、渲染快照。纯快照渲染下，从按键到看到结果是 RTT/2 + 半个 tick；打开预测后本地立即响应，但收到权威快照时可能被校正回弹；打开插值后画面平滑，代价是看到更久以前的世界。

回滚重放（Rollback / GGPO）

本地立即执行自己的输入；对方输入还没到，就先按「重复上一帧」预测，把画面跑下去。等到真实输入到达，如果预测错了，就回滚到那一帧、用真输入重放到当前帧 —— 用 CPU 换掉了「等帧」的延迟。
