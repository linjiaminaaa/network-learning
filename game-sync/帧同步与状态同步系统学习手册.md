## 1. 总览：同一个问题，两条路线

> **一句话结论**：所有网络同步都在解决「多个进程如何对同一个世界达成一致」，帧同步把一致性压在**确定性模拟**上，状态同步把一致性压在**权威服务器**上。

### 1.1 同步到底在同步什么

把「同步」拆开，其实是四件不同的事，两条路线对它们的处理方式完全不同：

| 要同步的东西 | 含义 | 帧同步怎么处理 | 状态同步怎么处理 |
|---|---|---|---|
| **权威** Authority | 谁说了算 | 无中心权威，靠「相同输入 + 相同代码 = 相同结果」的数学约定；服务器只做校验 | 服务器是唯一真相源，客户端无权改状态 |
| **输入/意图** Intent | 玩家这一帧想干什么 | **直接广播**（这是唯一的大流量数据） | 上行单播给服务器，不下发 |
| **状态** State | 世界当前长什么样 | **不传输**，各端本地算出来 | **传输**（全量/增量/脏标记） |
| **时间** Time | 第几帧、什么时候执行 | 帧号即时间；帧号推进由「输入是否凑齐」决定 | 服务器 tick 是时间源；客户端做时钟估计 |
| **随机与事件** Random/Event | 暴击、掉落、技能判定 | 随机必须**确定性种子**；事件由模拟产生 | 随机在服务器产生，客户端只收结果 |

这张表是全书的总纲。后面每一章都是在回答：这四件事中某一件，在某种约束下应该怎么处理。

### 1.2 本质差异：同步「指令」vs 同步「结果」

- **帧同步（lockstep / deterministic lockstep）**：同步的是**指令**（输入）。所有客户端本地跑**同一份确定性模拟**，只要输入序列一致，状态就必然一致。网络只承担「把每个人的输入按帧号归并后发给所有人」。
- **状态同步（state synchronization / snapshot replication）**：同步的是**结果**（状态）。服务器跑唯一一份模拟，周期性把状态（或其变化量）复制给客户端。客户端本质上是个「高刷新率的观众」，再加上预测来掩盖延迟。

由此推出两条最重要的工程结论：

1. **带宽随什么增长**：帧同步的带宽 ∝ 玩家数 × 输入帧率（与场上单位数几乎无关）；状态同步的带宽 ∝ 可见实体数 × 快照率 × 每实体字节数。
2. **谁是真相源**：帧同步里「真相」是分布式的、由数学保证的，任何一端算错都会分叉（desync）；状态同步里「真相」是集中的，客户端只能「看起来不对」，不会把世界带偏。

### 1.3 两条数据流对照图

```text
帧同步（只传输入，各端自己算）                    状态同步（服务器算，客户端看）

  C1 输入 ─┐                                        C1 输入 ──► ┌──────────┐
  C2 输入 ─┼─► 归并/中继（服务器或 Peer）─► 帧 f 输入集 ┤            │  服务器   │
  C3 输入 ─┘         │                                C2 输入 ──► │ 权威模拟  │
                     ▼                                          │ tick 20Hz │
        每个客户端本地 step(f) 确定性模拟                        └────┬─────┘
                     │                                                │ 快照/增量
                     ▼                                                ▼
        本地状态 = 他人状态（逐位相同）                      C1/C2/C3 收快照 → 插值 → 渲染
        每 K 帧上报哈希，服务器抽查                            客户端另有「预测 + 校正」回路
```

关键差别在图的右下角：帧同步客户端**自己算**，状态同步客户端**等别人算**（但会预测）。这决定了二者的失败模式完全不同——前者怕「算得不一样」，后者怕「看得太晚」。

### 1.4 一个常见误解先破掉

「帧同步不用服务器」是错的。生产环境的帧同步几乎总有一个服务器，只是它不模拟世界，而是做四件事：**输入归并/转发、丢包补发、回放校验（跑一份影子模拟）、断线快照**。它不决定游戏结果，但决定你能不能上线。

## 2. 时间、帧与 tick：一切的地基

> **一句话结论**：网络同步的第一性原理不是「发什么包」，而是「什么时候执行第几帧」——**逻辑帧必须固定步长，且由网络事件而非本地墙钟推进**。

### 2.1 逻辑帧 vs 渲染帧

| 概念 | 频率 | 由谁驱动 | 干什么 | 是否影响游戏结果 |
|---|---|---|---|---|
| **逻辑帧**（logic frame / tick / simulation step） | 固定，如 15/20/30/60 Hz | 帧同步：输入凑齐；状态同步：服务器定时器 | 执行一次 `step()`：读输入、跑物理/AI/技能、推进时间 | **是**，必须每端完全一致 |
| **渲染帧**（render frame） | 不固定，60–144+ Hz | 显卡 vsync / 浏览器 rAF | 把状态画出来，做插值 | 否，只是表现 |
| **服务器 tick** | 固定，如 20/30/60 Hz | 服务器主循环 | 权威模拟一次 | 是（它就是权威） |
| **快照帧**（snapshot rate） | 常低于 tick，如 10–30 Hz | 服务器序列化节流 | 把状态打包下发 | 否，是采样 |

这三者**解耦**是所有网络游戏的基本功。把渲染帧当逻辑帧（`dt = 上一帧耗时`）是新手最常犯的错：同一段游戏在 60 fps 和 144 fps 的机器上会跑出不同结果，帧同步直接分叉，状态同步则物理行为不一致。

### 2.2 固定步长循环 + 累加器

```python
DT = 1.0 / 30.0          # 逻辑帧间隔，固定
MAX_CATCHUP = 5          # 单帧最多追几步，防止死亡螺旋

acc = 0.0
prev, cur = None, None
last = now()
while running:
    frame_time = now() - last
    last = now()
    acc += frame_time
    if acc > MAX_CATCHUP * DT:      # 落后太多就丢弃时间
        acc = MAX_CATCHUP * DT
    while acc >= DT:
        prev, cur = cur, step(DT)   # 唯一的模拟入口，步长恒定
        acc -= DT
    alpha = acc / DT                # 0..1，帧间插值因子
    render(lerp(prev, cur, alpha))  # 渲染只读，不改逻辑状态
```

要点：

- **`step(DT)` 是纯函数式入口**：给定 `(状态, 帧号, 输入集)` 必然得到唯一的下一状态。这是帧同步的契约，也是回滚（第 6 章）能工作的前提。
- **`MAX_CATCHUP` 是必需的**：如果一帧耗时 200ms，死循环补帧会让下一帧更慢，形成「死亡螺旋」（spiral of death）。截断的代价是游戏时间变慢，但比卡死好。
- **`alpha` 只给渲染用**：逻辑永远在整帧上执行，视觉上用插值消除「逻辑 30Hz、屏幕 144Hz」的抖动。

### 2.3 为什么必须固定 tick

四个理由，按重要性排序：

1. **确定性**：浮点运算 `f(0.0333)` 与 `f(0.0166)` 累加出的轨迹必然不同。变步长 = 放弃「同输入同结果」。即使全是整数运算，变步长也意味着每帧执行的逻辑量不同，无法逐帧对齐。
2. **可重放**：回放 = 帧号 + 输入序列。只有步长固定，回放才能重现；状态同步的服务端回放校验（第 5 章）也依赖这一点。
3. **物理稳定**：固定步长的积分器行为可预测；变步长会让约束求解在低帧率下抖动甚至爆炸。
4. **网络对齐**：帧号是唯一可靠的公共时间轴。延迟、抖动、时钟漂移都在它之外被吸收。

### 2.4 tick 频率怎么选

| 频率 | Δt | 帧同步输入延迟下界（提前 2 帧发送） | 典型用途 | 代价 |
|---|---|---|---|---|
| 10 Hz | 100 ms | ~200 ms | 老 RTS、回合制小局、弱网卡牌 | 操作「粘」，不适合动作 |
| 15 Hz | 66.7 ms | ~133 ms | 移动端 RTS、部分 MOBA 逻辑层 | 手感偏钝 |
| 20 Hz | 50 ms | ~100 ms | 常见折中；移动端 MOBA / SLG 战斗 | 精细操作需预测补偿 |
| 30 Hz | 33.3 ms | ~67 ms | 主流 MOBA / 动作类帧同步 | CPU 与带宽上升 |
| 60 Hz | 16.7 ms | ~33 ms | 格斗游戏 rollback、FPS 服务器 tick | 成本最高，通常与状态同步搭配 |

选型口诀：**延迟下界 ≈ 输入提前帧数 × Δt**，先定手感容忍的延迟，再定帧率。比如能接受 100ms 输入延迟，就用 20Hz + 提前 2 帧；要 50ms 以内，只能上 60Hz 或者放弃纯帧同步（见第 11 章）。

> 「经验量级」：帧同步逻辑帧常见 15–30Hz，格斗 rollback 常见 60Hz，RTS 历史实现有 10Hz 级。

### 2.5 服务器时间与 RTT 估计

客户端不能相信本地墙钟，需要估计「服务器现在处在第几 tick / 什么时间」。最朴素也最常用的做法是**带时间戳的 ping-pong**：

```text
客户端 t0 发送 ping
服务器 t1 记录并原样回 timestamp（或带服务器时间）
客户端 t3 收到，单次样本 RTT = t3 - t0
```

工程上不直接用单次 RTT（抖动大），用指数滑动平均（与 TCP 的 SRTT 思路同源）：

```text
SRTT   = (1 - α) * SRTT + α * RTT_sample      # α 常见 1/8
RTTVAR = (1 - β) * RTTVAR + β * |SRTT - RTT_sample|   # β 常见 1/4
```

服务器时间偏移估计：

```text
offset ≈ ((t1 - t0) + (t1' - t3)) / 2
其中 t1' 为客户端收到的服务器时间戳（需同一时钟域）
误差上界 ≈ 单次 RTT / 2（假设上下行对称，这条假设在移动网络里经常不成立）
```

因此**不要在延迟预算里把 `RTT/2` 当成精确值**，要留抖动余量（见 2.7）。

### 2.6 时钟漂移

晶振精度通常几十 ppm（parts per million）。算一下：1 ppm 相对误差意味着每秒差 1 微秒，一小时差 3.6 ms。**100 ppm 的偏差一小时就是 360 ms**——相当于一整个逻辑帧还多。

两种处理思路：

| 场景 | 做法 | 为什么 |
|---|---|---|
| 帧同步 | **逻辑帧不由本地墙钟推进**，而由「输入是否齐」推进；本地时钟只用于渲染插值和超时判定 | 漂移根本不影响模拟结果，因为时间轴是帧号 |
| 状态同步 | 客户端用服务器时间做插值时间轴；本地时钟只做短时外推；定期用服务器时间校正，并**限制单次校正幅度**（如每帧 ≤5% 时间缩放） | 直接跳时间会让画面「弹一下」 |

如果需要客户端主动追服务器时间，常见实现是**轻微调整**：慢一点就每帧多等一点点（time dilation），快一点就少等一点点，把误差摊在几十帧里消化，而不是一次性对齐。

### 2.7 延迟预算怎么分配

**帧同步端到端输入延迟**（从玩家按键到本地看到反馈）：

```text
L_lockstep ≈ F_input × Δt          # 输入提前发送的帧数，常见 1–3 帧
           + RTT                    # 自己的输入到别人、再回到自己（往返）
           + F_jitter × Δt          # 抖动导致的额外等待
           + 渲染插值延迟
```

**状态同步端到端输入延迟**：

```text
L_statesync ≈ RTT/2                # 输入上行 + 结果下行的一半（对称假设）
            + F_snap × Δt_snap     # 服务器 tick 等待 + 快照排队（常见 1–2 个快照间隔）
            + D_interp             # 客户端插值缓冲（第 10 章，常见 100–200 ms）
            - 预测掩盖量            # 本地预测让「自己的操作」看起来接近 0 延迟
```

| 预算项 | 帧同步（30Hz，RTT 80ms，提前 2 帧） | 状态同步（tick 20Hz，RTT 80ms，插值 100ms） |
|---|---|---|
| 输入采集 + 提前量 | 67 ms | 0（预测立即生效） |
| 上行网络 | 40 ms（含在 RTT 内） | 40 ms |
| 服务器排队 / tick | ≤33 ms | ≤50 ms |
| 下行网络 | 40 ms（含在 RTT 内） | 40 ms |
| 客户端插值 / 缓冲 | 0（本地立即执行） | 100 ms |
| **玩家感知的「自己操作」延迟** | **约 70–110 ms** | **约 0–50 ms（预测）** |
| **玩家感知的「别人动作」延迟** | 约 70–110 ms（与所有人一致） | 约 150–230 ms |

这张表解释了为什么 FPS/MOBA 选状态同步 + 预测：**自己的操作必须跟手**；也解释了为什么帧同步在「操作手感」上天生吃亏，它的优势在一致性与带宽。

## 3. 帧同步原理

> **一句话结论**：帧同步用「确定性的本地模拟 + 只广播输入」换取极低带宽与天然一致的状态，代价是**延迟、确定性工程和容错设计**。

### 3.1 核心思想

两个假设撑起整套方案：

- **假设 A（确定性）**：同样的初始状态 + 同样的输入序列 + 同样的代码与数据 = 逐位相同的结果。
- **假设 B（归并）**：所有客户端在同一帧上使用**完全相同的一组输入**。

只要 A、B 成立，网络就只需要传「谁在第几帧按了什么」，状态不需要传。由此得到帧同步的三大好处：

1. **带宽与实体数解耦**：1000 个小兵的 RTS，每帧传的还是那几个玩家的点击。
2. **状态天然一致**：不存在「服务器状态和客户端状态谁对」的问题，只有「有没有分叉」。
3. **回放几乎免费**：回放文件 = 初始种子 + 输入序列，常见只有几 KB（RTS 经典 demo 的量级）。

代价同样明确：延迟（必须等输入凑齐）、确定性工程（第 4 章）、作弊空间（输入全广播，等于告诉对手你在干什么，第 5 章）。

### 3.2 一帧的完整生命周期

以 4 人房、20Hz 逻辑帧、客户端以 2 帧提前量发送输入为例（**编号步骤，生产实现可能合并/拆分**）：

1. **采集**：客户端在第 `f` 帧收集本地输入，得到 `input(f)`（按键位域 + 摇杆量化值 + 帧号）。
2. **加偏移**：确定这条输入要作用在未来的第 `f + F_input` 帧，包内写明 `target_frame = f + 2`。
3. **打包**：把一个输入包做成 `{header, [target_frame, input, target_frame-1, input_prev, ...]}`，携带最近 N 帧冗余（第 5 章）。
4. **上行**：UDP 单播给服务器（或 peer 全连接）。包本身不保证到达。
5. **归并**：服务器按 `target_frame` 把各玩家输入放进帧表 `inputs[target_frame][player]`；同帧重复包按「先到者为准 / 后到者覆盖」需统一策略（常见是先到为准，保证确定性）。
6. **凑齐判定**：当 `inputs[target_frame]` 中所有存活玩家的输入都到齐（或超时用托管输入填充），该帧标记为 ready。
7. **广播**：服务器把该帧的**完整输入集合**发给所有客户端。可顺带广播未来若干帧已就绪的输入，降低后续等待。
8. **入缓冲**：客户端收到后写入本地帧缓冲 `frame_buffer[target_frame]`，重复帧丢弃。
9. **取帧执行**：客户端主循环检查 `frame_buffer[cur_frame]` 是否就绪；就绪则取出来，`step(cur_frame, inputs)`。
10. **推进**：`cur_frame += 1`；若缓冲区里还有就绪帧可以连续执行（见 3.6 追帧）。
11. **校验**：每 K 帧（常见 K=10–60）计算一次确定性哈希 `hash(state)`，随下一个输入包或独立包上报给服务器。
12. **对比**：服务器用同一份代码跑影子模拟，比对哈希；不一致则记录/告警/踢出/回灌快照（第 5 章）。

> 注意第 5 步和第 6 步是帧同步服务器存在的**唯一必要理由**：没有它，玩家之间的 NAT 穿透、输入补发、哈希校验、断线重连都无处落地。

### 3.3 输入采集：帧号 + 偏移

输入结构通常长这样（位域打包，见第 8 章的同类技巧）：

```c
typedef struct {
    uint16_t target_frame;   // 这条输入要作用在哪一帧
    uint16_t player_id;
    uint32_t buttons;        // 按键位域：移动/攻击/技能/取消...
    int16_t  move_x, move_y; // 摇杆量化到 [-32767, 32767]
    uint16_t checksum;       // 可选：输入包自身校验
} InputCmd;
```

三个细节决定手感与稳定性：

- **帧号必须显式携带**，不能靠「到达顺序」推断。乱序、丢包、重发都会让顺序失真。
- **提前量 `F_input` 是手感与抗抖动的调节旋钮**：太小则弱网下频繁等帧（卡顿），太大则输入延迟增加。常见 1–3 帧。
- **输入值必须量化成整数**（摇杆用定点），不能让「原始浮点摇杆值」进入模拟——那会把平台差异带进确定性（第 4 章）。

### 3.4 帧广播与冗余帧

UDP 会丢包，而帧同步**不能丢输入**：少一条输入，那一帧就永远算不出来。所以每个输入包都携带**最近 N 帧的输入记录**（冗余帧 / redundant frames），接收方按帧号去重。常见 N=3–10，代价是带宽线性上升，通常仍远小于状态同步。

也可以**每条输入重复发送 M 次**（不加冗余历史，只是重发同一帧），实现更简单，但抗连续丢包能力差。生产实现多选「冗余历史」。

### 3.5 等帧与卡顿归因

帧同步的卡顿有一个专门名词：**等帧**（stall / hiccup）。表现是画面里的单位和 UI 短暂停住，然后突然「快进」补上。归因时必须分清：

| 现象 | 原因 | 是否可接受 | 对策 |
|---|---|---|---|
| 频繁小停顿（<100ms） | 某个玩家上行抖动大、输入晚到 | 体验尚可 | 增大提前量、冗余帧、自适应 buffer |
| 长停顿后快进 | 某玩家丢包/断线，等超时 | 需要兜底 | 超时托管（3.7） |
| 只有某玩家卡 | 他的上行链路差，或客户端算得慢 | 局部 | 加托管、提示网络状态 |
| 所有人周期性卡 | 服务器归并线程或房间主循环抖动 | 全局 | 服务器侧排查（第 12 章） |
| 画面不卡但位置「瞬移」 | 追帧一次补太多帧 | 观感差 | 限制单次追帧数、分帧补 |

一个重要的产品判断：**帧同步的卡顿是「全局可见」的**——一个人卡，全房间等。这也是很多团队最终转向状态同步的原因（状态同步里一个人卡只影响他自己）。

### 3.6 追帧 catch-up

当本地落后服务器帧号超过阈值（例如 10 帧），需要快速追上：连续执行 `step()`，但不渲染中间帧，直到追上或达到单帧时间预算上限。

```python
def catch_up(cur, target, budget_ms=8):
    start = now()
    while cur.frame < target:
        if elapsed_ms(start) > budget_ms:   # 别把主线程卡死
            break
        cur = step(cur.frame + 1, buffer.pop(cur.frame + 1))
    return cur
```

工程注意：

- **追帧期间必须禁用渲染插值**，否则画面会「抽搐」。
- **追帧要有上限**：落后 300 帧时一口气追上可能耗时几百 ms，应分多帧追，并优先保证「不再落后」。
- **追帧与回滚不同**：追帧是「向后执行已知帧」，回滚是「退回到旧状态再重跑」（第 6 章）。

### 3.7 空帧与托管

如果某玩家在超时窗口（常见 100–300ms，约 2–6 个逻辑帧）内没送来第 `f` 帧输入，服务器必须替它填一个值，否则全房间停摆。两种策略：

| 策略 | 填什么 | 后果 |
|---|---|---|
| **空帧**（empty input） | 全 0 输入（不动不攻击） | 确定、公平，但玩家回来时会「丢了一段操作」 |
| **托管 / 复制上一帧**（last-input repeat） | 重复其最后一帧输入 | 手感更连贯，但可能让角色一直朝墙走 |

无论哪种，**填的值必须由服务器广播给所有人**（或由所有人用同一规则在本地推导），否则各端填的值不同，立刻 desync。推荐做法：服务器广播一个显式的「托管帧」事件，客户端不再自己猜。

## 4. 确定性工程（帧同步的真正难点）

> **一句话结论**：确定性不是「让浮点变准」，而是**消除一切跨环境差异**——浮点不是天生不可靠，真正杀人的是超越函数实现、编译器重排/FMA、跨架构、未初始化内存与容器遍历顺序。

### 4.1 确定性的定义与分级

| 级别 | 含义 | 是否够用 |
|---|---|---|
| **结果确定** | 同输入得到同**语义**结果（位置误差 <1cm） | 不够，误差会累积到分叉 |
| **逐位确定**（bit-exact） | 同输入得到**逐字节相同**的快照与哈希 | 帧同步的硬要求 |
| **跨平台逐位确定** | 不同 CPU/编译器/OS/JS 引擎之间也逐位相同 | 商业项目的目标，最难 |

帧同步要的是第三级。判断手段是**状态哈希**：每 K 帧对关键状态做一次哈希（FNV-1a / xxHash / CRC32 都行，只要能稳定复现），服务器与客户端比对。

```python
def state_hash(state):
    h = 2166136261            # FNV-1a 32-bit offset basis
    for v in state.serialize_deterministic():   # 定点整数 / 有符号字节
        h ^= v & 0xFF
        h = (h * 16777619) & 0xFFFFFFFF
    return h
```

要点：

- **哈希的对象必须是「模拟状态」**，不是渲染状态、不是内存镜像（内存里有 padding、指针、vtable）。
- **序列化顺序必须固定**（按实体 ID 排序，不用哈希表遍历顺序）。
- **哈希本身用整数运算**，别用浮点参与。
- 第一个不一致的帧号就是**分叉点**，这是排查的起点（4.9）。

### 4.2 浮点到底哪里不可靠

先把一个流传很广的错误说法纠正掉：**IEEE 754 的基本运算（+ − × ÷ √、比较）是正确舍入的，因此给定相同输入与相同舍入模式，结果逐位确定**。也就是说，纯 `+ - * /` 的浮点代码在同一架构上重复运行是确定的。

真正的问题出在这些地方：

| 杀手 | 机制 | 典型表现 | 对策 |
|---|---|---|---|
| **libm 超越函数** | `sin/cos/atan2/exp/pow/log` 不在 IEEE 754 强制舍入范围内，各 libm 实现精确到「最后 1 ulp 不同」 | 同一角度算出相差 1e-16 的值，几千帧后分叉 | 自己做查表 + 定点插值，或 CORDIC（4.6） |
| **编译器重排 / 收缩** | `a*b+c` 被编译成 FMA（一次舍入）或反之；`(a+b)+c` 被改成 `a+(b+c)` | 同源码不同编译选项结果不同 | 禁 `-ffast-math`；帧同步关键路径用整数/定点 |
| **x87 80 位扩展精度** | 32 位 x86 上中间结果可能以 80 位寄存器保存，写回内存才截断 | 同代码在 32 位与 64 位机器上结果不同 | 用 SSE/`-mfpmath=sse` 或干脆定点 |
| **`-ffast-math` / `-Ofast`** | 允许假定无 NaN/Inf、允许重排、允许用倒数近似指令 | 结果与精确语义不同，且随优化级别变化 | 帧同步模块禁用 |
| **跨架构差异** | ARM NEON 与 x86 SSE 的基本运算其实一致，但：不同 libm、denormal 处理（FTZ/DAZ）、`float` 与 `double` 的中间精度假设、编译器内置函数不同 | 移动端与 PC 端分叉 | 定点 + 自有数学库 + 避免 denormal |
| **未初始化内存** | 读未初始化变量/结构体 padding | 值随调用栈历史变化，表现为「偶发 desync」，最难查 | 全部初始化；序列化不碰 padding；用 sanitizer |
| **NaN / Inf 传播** | 一旦出现 NaN，比较全为 false，分支走向随实现而异 | 位置变 NaN，角色消失/飞天 | 断言 + 兜底（把 NaN 钳成 0 并记录） |
| **float→int 转换溢出** | C/C++ 里越界转换是 UB | 不同优化结果不同 | 钳位后再转 |
| **有符号整数溢出** | C/C++ 里 UB，编译器可假定不发生 | 优化后行为诡异 | 用无符号或显式检查 |
| **时间依赖** | `dt` 用真实耗时、`rand()` 用时间种子 | 每台机器不同 | `dt` 恒定；随机用固定种子 |
| **容器遍历顺序** | `unordered_map`/`dict`/`HashSet` 的桶顺序受哈希种子、插入历史影响 | 迭代顺序不同 → 运算顺序不同 → 结果不同 | 用有序容器；或迭代前按 ID 排序 |
| **排序不稳定** | `qsort`/快速排序对相等元素顺序不保证 | 同分值的实体顺序不同 | 用稳定排序，或排序键包含唯一 ID |
| **指针 / 地址参与逻辑** | 用对象地址做哈希、排序、去重 | ASLR 每次运行不同 | 用 ID 不用地址 |
| **线程/并行执行顺序** | 多线程求和的累加顺序不同 | 同帧结果不同 | 帧同步用单线程逻辑，或固定归约顺序 |

> 结论：**能用整数就不用浮点；必须用浮点时，把「所有非 IEEE 基本运算」都换成自己的确定性实现。**

### 4.3 逐帧哈希验证的工程做法

生产上的确定性监控通常是三层：

1. **帧内断言**（开发期）：坐标在合法范围、没有 NaN、血量非负、实体数不超上限。
2. **每 K 帧哈希**（运行期）：客户端上报 `(frame, hash)`，服务器运行影子模拟（shadow simulation）比对。
3. **分叉快照**（故障期）：一旦不一致，服务器要求双方上传该帧完整状态（或服务器直接下发权威快照并记录），把 desync 转成可复现的 bug 单。

哈希上报的频率是带宽与灵敏度的权衡：K 太小浪费带宽，太大则很难定位「到底哪一帧开始错」。常见 K=10–60。

### 4.4 定点数：为什么是 Q16.16

定点数用整数表示小数：`value = int_raw / 2^fraction_bits`。Q 格式记作 `Qm.n`（m 位整数、n 位小数），Q16.16 就是「32 位有符号、低 16 位是小数」。

| 属性 | Q16.16（int32） | Q32.32（int64） |
|---|---|---|
| 小数位数 | 16 | 32 |
| 分辨率（最小步长） | `1/65536 ≈ 1.526×10⁻⁵` | `2.33×10⁻¹⁰` |
| 有符号范围 | `[-32768, 32767.99998]` | 约 `[-2.1×10⁹, 2.1×10⁹]` |
| 乘法中间值 | `int32 × int32 = int64`，安全 | 需 128 位（`__int128` 或双 64 位拆分） |
| 加/减法 | 直接整数加减，溢出检查 | 同 |
| 适合表示 | 角度、朝向、单位向量分量、速度、UI 参数 | 世界坐标、长时间累计量 |

**为什么不是 Q8.24 / Q24.8**：小数位太少则精度差（Q24.8 分辨率 3.9e-3，位置会抖）；整数位太少则范围小。Q16.16 在 32 位里是「范围够用 + 精度够用」的经典折中。

**关键工程问题：范围不够怎么办？** Q16.16 最大只能表示约 ±32767。若 1 单位 = 1 米，地图只有 32 公里；若 1 单位 = 1 厘米，只有 327 米。常见解法：

| 解法 | 做法 | 代价 |
|---|---|---|
| 提高小数位 | 用 Q32.32 / Q48.16 | 位宽上升，乘法要 128 位 |
| **分块坐标**（chunk-local） | 世界按区块划分，模拟时用区块内局部坐标，只在大地图查询时加偏移 | 跨块边界处要特判 |
| 单位缩放 | 1 单位 = 1 米，用 Q16.16 且接受 1.5e-5 米精度 | 远距离叠加误差相对可接受 |

> 经验量级：RTS/MOBA 的坐标常用「毫米或厘米为单位的整数」，Q16.16 用于朝向/角度/方向向量、物理的中间量，而坐标本身用 int32/int64 整数。

### 4.5 定点数四则运算与开方（含溢出边界）

记 `ONE = 1 << 16 = 65536`，`a, b` 为原始整数。

**加法 / 减法**：直接整数加减，唯一风险是溢出：

```c
// Q16.16 add，返回是否溢出
static inline int32_t q_add(int32_t a, int32_t b, int *ovf) {
    int64_t r = (int64_t)a + b;
    if (r > INT32_MAX || r < INT32_MIN) { *ovf = 1; return 0; }
    *ovf = 0;
    return (int32_t)r;
}
```

范围分析：`|a + b| ≤ 2^31 − 1` 才不溢出，即两个操作数之和的**整数部分**不能超过 32767。

**乘法**：

```c
// Q16.16 mul，四舍五入（向 +∞ 取整）
static inline int32_t q_mul(int32_t a, int32_t b) {
    int64_t p = (int64_t)a * (int64_t)b;    // |p| ≤ 2^62，int64 装得下
    return (int32_t)((p + 0x8000) >> 16);   // 算术右移，负数向 -∞ 取整
}
```

边界分析：

- 中间积最大 `2^31 × 2^31 = 2^62 ≈ 4.6×10^18`，`int64` 上限约 `9.22×10^18`，**安全**。
- 结果必须落在 `int32` 内，即 `|a/ONE| × |b/ONE| ≤ 32767.99`。例如 `200 × 200 = 40000` 会溢出，`-32768 × -32768` 也会。
- 舍入偏移 `+0x8000` 对负数会偏向 -∞ 取整（`floor` 语义），**这不是「数学上最近的整数」，但它是确定性的**——帧同步要的正是确定性。若要求严格四舍五入（远离零），需要按符号分别加偏置。
- 高 16 位可能被 `-1 × -1` 这类情况影响，检查时用 `int64` 判定结果范围。

**除法**：

```c
// Q16.16 div，先做溢出检查
static inline int32_t q_div(int32_t a, int32_t b, int *ovf) {
    if (b == 0) { *ovf = 1; return 0; }              // 必须显式处理除零
    int64_t num = ((int64_t)a) << 16;
    int64_t q = num / b;
    if (q > INT32_MAX || q < INT32_MIN) { *ovf = 1; return 0; }
    *ovf = 0;
    return (int32_t)q;
}
```

边界分析：

- 溢出条件：`|a| ≥ |b| × 32768`，等价于结果的整数部分超过 32767。典型触发：除以一个小于 1 的数（如 `a / 0.001`）。
- `a = -32768.0`（即 `INT32_MIN`）时左移 16 位会溢出 64 位？`INT32_MIN << 16 = -2^47`，在 int64 内安全；但 `a << 16` 若用 int32 就 UB，**必须先转 int64**。
- 整数除法向零截断，**统一方向即可**；不要在 x86（向零）和 ARM（也向零）之间混用不同语义的自定义实现。
- 除零必须显式定义（返回 0 / 饱和到最大 / 触发断言），否则不同平台行为不同甚至崩溃。

**开方**：两种确定性实现。

思路一：整数位逐位开方（digit-by-digit），完全用整数位运算，天然确定：

```c
// 求 sqrt(x)，x 为 Q16.16，结果 Q16.16
// 等价于求 isqrt((uint64_t)x << 16)
static uint64_t isqrt64(uint64_t v) {
    uint64_t rem = 0, root = 0;
    for (int i = 31; i >= 0; --i) {      // 逐位确定
        root <<= 1;
        rem = (rem << 2) | ((v >> (2 * i)) & 3);
        if (root < rem) { rem -= root + 1; root += 2; }
    }
    return root >> 1;
}
```

思路二：牛顿迭代 + 固定次数（**次数固定才确定**）：

```text
x_{n+1} = (x_n + S / x_n) / 2      // 定点除法，见上
初始猜测 x_0 = 1 << 16（或按位宽取 2 的幂）
迭代 5–6 次后达到 16 位精度（误差随迭代平方收敛）
```

边界分析：`S = 0` 时 `S / x_n = 0`，迭代收敛到 0（注意 `x_n` 不能为 0，初值取 1 即可）；`S < 0` 必须先断言（负数的平方根无定义）；`S` 很大时 `x_0` 取太小会收敛慢，取 `x_0 ≈ 2^((bitlen(S))/2)` 可保证次数。

**三角函数**：见 4.6。

### 4.6 确定性三角函数

三种方案，按精度/成本排序：

| 方案 | 原理 | 精度 | 成本 | 适用 |
|---|---|---|---|---|
| **查表（无插值）** | 预生成 `sin[i]`，`i = angle / (2π/N)` | 量化误差 = 表分辨率 | 最低 | 粗精度、低帧预算 |
| **查表 + 线性插值** | `sin(θ) ≈ t[i] + (t[i+1]-t[i]) × frac` | 误差 ≈ `(Δθ)²/8`（二阶导绝对值 ≤ 1） | 低 | 大多数游戏 |
| **CORDIC** | 用 `arctan(2^-i)` 表的旋转迭代，只做移位/加减 | 由迭代次数决定（每轮 ~1 bit） | 中 | 需要高精度且无表时 |

查表 + 线性插值的误差推导：把 `sin` 在一段宽度 `Δθ = 2π/N` 内用弦近似，最大误差约为 `(Δθ)²/8`（因为 `|sin''| ≤ 1`）。取 `N = 4096`：`Δθ ≈ 1.534×10⁻³`，误差 ≈ `2.9×10⁻⁷`——**远小于 Q16.16 的分辨率 1.5×10⁻⁵**，所以对 Q16.16 来说「表 + 插值」已经足够，瓶颈反而是量化本身。取 `N = 1024`：`Δθ ≈ 6.1×10⁻³`，误差 ≈ `4.7×10⁻⁶`，仍在 Q16.16 分辨率之下。

```c
// 4096 项表，Q16.16 存储；角度用「二进制角」表示（0..65535 对应 0..2π）
static int32_t q_sin(uint16_t angle) {          // 角度单位：1/65536 圈
    uint32_t idx  = (uint32_t)angle * 4096 >> 16; // 取高 12 位作索引
    uint32_t frac = ((uint32_t)angle << 12) & 0xFFFF; // 低 12 位作插值尾数
    int64_t a = SIN_TABLE[idx], b = SIN_TABLE[(idx + 1) & 4095];
    return (int32_t)(a + (((b - a) * (int64_t)frac) >> 16));
}
```

要点：**角度不要用弧度浮点**，用「二进制角」（把一圈分成 2^16 或 2^32 份的整数）。查找表用整数生成脚本（离线算好、提交进仓库），保证所有平台用同一张表。

CORDIC 的确定性来自「只用移位和加减」：

```text
输入角度 z，初始 x=K, y=0
重复 i = 0..N-1：
    d = (z >= 0) ? +1 : -1
    x' = x - d * (y >> i)
    y' = y + d * (x >> i)
    z' = z - d * atan_table[i]     # atan 值预先定点化
输出 (x, y) 即 (cos, sin)，增益 K 由迭代次数决定，预先乘回
```

代价是每轮一次查表 + 三次加减/移位；15 轮左右可到 16 位精度。

### 4.7 确定性随机

帧同步的随机必须满足：**同种子、同消耗顺序 → 同序列，且跨平台逐位一致**。

| 算法 | 状态 | 运算 | 特点 |
|---|---|---|---|
| **LCG**（线性同余） | 32/64 位整数 | `x = (a*x + c) mod 2^32` | 最简单；低位质量差（不要取 `x % 2` 之类） |
| **PCG32** | 64 位 + 增量 | `state = state*6364136223846793005 + inc`，输出用 xorshift + 旋转 | 质量好、快、常见于游戏 |
| **xorshift / splitmix** | 32/64 位 | 纯移位异或 | 极快，质量尚可 |
| **Mersenne Twister** | 2.5KB 状态 | 大量位运算 | 质量高但状态大，回滚快照成本高 |

```c
// PCG32 风格的确定性随机（简化示意）
typedef struct { uint64_t state, inc; } Rng;
static uint32_t rng_next(Rng *r) {
    uint64_t old = r->state;
    r->state = old * 6364136223846793005ULL + r->inc;   // 无符号回绕，定义明确
    uint32_t xs = (uint32_t)(((old >> 18) ^ old) >> 27);
    uint32_t rot = (uint32_t)(old >> 59);
    return (xs >> rot) | (xs << ((32 - rot) & 31));
}
```

三个必须遵守的纪律：

1. **无符号整数回绕**在 C/C++ 里定义明确；**有符号溢出是 UB**，所以 RNG 内部一律用 `uint32/uint64`（Python 里要手动 `& 0xFFFFFFFF`，因为 Python 的整数无溢出）。
2. **随机数的消耗顺序必须与逻辑顺序一致**：不能「先给所有单位各掷一次，再按 ID 排序处理」而让顺序依赖容器遍历（4.2）。
3. **不要用「时间 / 指针 / 进程 ID」做种子**。种子由房间创建者（或服务器）生成并广播，回放时用它复现。

还有一个隐蔽的坑：**随机数不要跨帧共享隐式状态**。如果每帧的随机数由一个全局 RNG 流提供，那么任何一次「多掷/少掷」（比如某个条件分支只在客户端 A 成立）都会让后续所有随机数错位，分叉会立刻扩散。更稳的常见实现是**按（帧号, 实体ID, 用途）派生种子**的哈希随机（`hash(seed, frame, entity_id, purpose)`），这样每次取值互不影响。

### 4.8 容器的遍历顺序、排序与指针

```python
# 错：dict 遍历顺序在 Python 3.7+ 是插入序，看似稳定，
#     但插入顺序本身可能依赖网络到达顺序 → 不同机器不同
for unit in units_by_id.values():
    unit.update(dt)

# 对：显式按 ID 排序，顺序与到达历史无关
for uid in sorted(units_by_id):
    units_by_id[uid].update(dt)
```

同样的问题出现在：

- **哈希集合去重**后遍历（顺序随机）。
- **不稳定排序**：`qsort` 比较函数只比伤害值时，同伤害的两个单位顺序不保证；改为 `(damage, id)` 双键比较。
- **对象池复用**：新对象复用了旧对象的内存，如果没完全初始化，残留值会参与逻辑。
- **浮点累加顺序**：`sum(a)` 与 `sum(reversed(a))` 可能差 1 ulp。要逐位一致就必须固定顺序。

### 4.9 物理引擎跨平台确定性为什么难

物理引擎是浮点密集 + 迭代求解 + 大量容器操作的组合，几乎命中 4.2 的所有杀手：

| 环节 | 为什么难确定 |
|---|---|
| 碰撞检测宽相 | 空间哈希/树的遍历顺序影响「先处理哪对」 |
| 窄相 | 接触点生成顺序、法线方向在退化情况下不稳定 |
| 约束求解 | 迭代求解器的迭代顺序与收敛判据对浮点极敏感 |
| 积分器 | 浮点累积误差；变步长直接破坏确定性 |
| 休眠/唤醒 | 阈值比较，浮点噪声会改变实体是否休眠 |
| 多线程 | 求解器常并行，归约顺序不固定 |

商业上「物理确定性跨平台」几乎只有两条路：**自研整数/定点物理**（成本极高，常见于 RTS/竞技类），或**放弃物理确定性、只在同一平台内做帧同步**（同版本同硬件，风险可控），或**物理走状态同步、逻辑走帧同步的混合方案**（第 11 章）。

### 4.10 跨端一致性策略

| 策略 | 做法 | 适用 |
|---|---|---|
| **全整数/定点** | 模拟层禁止浮点，坐标/角度/物理全定点 | 强对抗、跨移动+PC、要长期维护 |
| **同版本锁定** | 客户端版本号强制一致，逻辑代码同源 | 通用做法，必须配合 |
| **浮点 + 自研数学库** | 只用 IEEE 基本运算 + 自有 sin/sqrt/pow，禁 fast-math | 3D 但物理简单 |
| **服务器权威兜底** | 定期下发权威快照覆盖客户端 | 作弊/分叉的保险丝 |
| **逻辑与表现分离** | 逻辑帧用定点，渲染层用浮点（插值） | 所有项目都该做 |

### 4.11 desync 排查方法论

按成本从低到高：

1. **定位分叉帧**：比对哈希上报序列，找到第一个不一致的帧 `f*`。这是最关键的一步，能砍掉 90% 的搜索空间。
2. **重放**：用服务器记录的输入序列在本地重放，若本地也复现，说明是「数据 + 代码」确定性问题；若本地复现不了，说明是**输入归并不一致**（更常见）。
3. **输入比对**：把分叉帧前后几帧的输入集合（每个玩家的每个字段）逐字节 diff。常见原因：托管填值不一致、丢包补发顺序不一致、重复包覆盖策略不一致、帧号偏移算错。
4. **状态二分**：如果输入一致但仍分叉，用「同一帧状态」二分：把分叉前 N 帧的状态快照互换（A 的状态给 B），看是否收敛。能定位到具体子系统（物理 / AI / 技能 / 随机）。
5. **平台差异定位**：在 PC 上能复现、手机上不能（或反过来）→ 查 libm、denormal、float 精度、编译器选项、未初始化内存。用 sanitizer（ASan/MSan/UBSan）扫一遍未初始化读。
6. **消融**：关掉 AI、关掉物理、关掉随机，逐个恢复，定位到最小复现。

| 现象 | 最可能原因 |
|---|---|
| 开局就分叉 | 初始状态不一致（种子、地图数据、实体创建顺序） |
| 第 1–2 帧就分叉 | 输入归并/排序问题 |
| 运行几十秒后分叉 | 浮点/超越函数/随机（累积误差） |
| 偶发、不可复现 | 未初始化内存、多线程顺序、哈希容器 |
| 只在某类设备分叉 | 架构/编译器细节（4.2） |
| 只在某人卡顿后分叉 | 托管/追帧逻辑 |

## 5. 帧同步的容错与安全

> **一句话结论**：帧同步的容错核心是「**永不丢输入、永不猜错输入**」——丢包用冗余帧补，断线用全量快照追，作弊用服务器回放校验兜底。

### 5.1 丢包与乱序

| 问题 | 后果 | 对策 |
|---|---|---|
| **丢包** | 该帧输入永远缺失 → 全房间等帧 | 冗余帧（3.4）、输入包重发、服务器补发 |
| **乱序** | 后发先至，帧表被写乱 | 帧号显式携带，按帧号插入而非按到达顺序 |
| **重复** | 同一帧被写入两次，若两次值不同则分叉 | 明确「先到为准」或「后到覆盖」策略，且**全端一致** |
| **迟到** | 超过等待窗口才到 | 已按托管执行 → 丢弃后到的真实输入，并记录（这叫「输入失效」） |

实现要点：帧缓冲是一个「按帧号索引的字典 + 一个已执行的最大帧号」。收到 `target_frame ≤ 已执行帧号` 的输入一律丢弃（已经在托管值上执行过了），否则写入缓冲。

### 5.2 可靠 UDP 的取舍

帧同步通常直接跑在 UDP 上，自己做一个「薄可靠层」：

| 机制 | 要不要 | 说明 |
|---|---|---|
| 序号 + 冗余帧 | **要** | 帧号天然是序号 |
| ACK / NACK | 要（可选） | NACK 更划算：只请求缺失帧 |
| 重传 | 要（有限） | 超过等待窗口的重传没有意义 |
| 按序交付 | 不要（应用层排序） | 帧号排序，传输层不必保证顺序 |
| 拥塞控制 | 弱 | 帧同步码率恒定且很低，常见只做发送限速 |
| 加密 | 要 | 输入可被伪造/篡改，至少防重放与篡改 |

> KCP / ENet 这类「可靠 UDP 库」都用了「序号 + ACK + 快速重传」的思路，但帧同步通常只需要其中很少一部分：**低延迟、冗余、允许丢弃过期数据**。

### 5.3 断线重连：全量快照 + 追帧

断线重连是最容易被低估的部分。重连客户端错过了 N 帧输入，不可能「从零重算」——必须给它一个**起始状态**。流程：

1. 客户端重连，带上自己的 `player_id` 与最后确认的帧号 `f_last`。
2. 服务器判定房间是否还在进行；若还在，准备一份**全量快照**（`frame = f_snap`，`f_snap` 为当前帧或稍早的「已确认帧」）。
3. 快照必须包含：完整实体状态、随机数状态、本局种子、实体 ID 分配器、计时器、待处理事件队列——**任何影响后续模拟的状态**。
4. 服务器把快照 + 从 `f_snap` 到当前的所有输入集合发给客户端。
5. 客户端从 `f_snap` 开始追帧（3.6），追上后恢复正常输入。
6. 重连期间该玩家的输入由托管填充（3.7），并广播给所有端。

| 快照策略 | 优点 | 缺点 |
|---|---|---|
| 服务器**常驻保存**每帧快照 | 重连快 | 内存大（每帧都存） |
| **定期快照**（每 30–60 帧）+ 之后的输入回放 | 内存可控 | 重连要追更多帧 |
| **状态同步式兜底**：帧同步失败时下发一次权威状态 | 最稳 | 需要维护两套状态结构 |

> 常见实现：服务器每 N 帧（或每局关键节点）做一次快照并异步持久化，重连时用「最近快照 + 输入回放」恢复。回放成本 = 追的帧数 × 单帧耗时，要在预算内（例如 60 帧 × 2ms = 120ms，可接受）。

### 5.4 观战与回放

**回放 = 输入序列**。这是帧同步最优雅的性质：

```text
replay = { 版本号, 地图/规则版本, 随机种子, 玩家列表, [帧号 → 每个玩家的输入] }
```

RTS 的经典整局 demo 常见只有几十 KB 到几百 KB，就是因为它只有输入。注意几个工程点：

| 问题 | 说明 |
|---|---|
| **版本兼容** | 改一行逻辑代码，旧回放就播不出来。常见做法：回放绑定版本号，客户端内置多版本模拟器（成本高），或接受「旧回放作废」 |
| **观战** | 观战者 = 一个「只收输入、不产出输入」的客户端；它可以比选手晚几秒开始（延迟观战），也可以只收服务器汇总状态（更省事） |
| **作弊视角** | 观战/全量输入会泄露「战争迷雾」信息。竞技比赛常用**延迟 + 裁剪**，或干脆用服务器录制的状态流 |
| **拖进度条** | 快进 = 从最近关键帧快照出发连续执行；否则从头算 |

### 5.5 防作弊

帧同步的作弊面比状态同步大，因为**输入是公开的**（所有客户端都收到所有人的输入）。风险与对策：

| 作弊类型 | 为什么可能 | 对策 |
|---|---|---|
| **改本地状态**（无敌、加速） | 客户端自己算状态 | 服务器影子模拟 + 逐帧哈希比对；不一致直接判负/踢出 |
| **伪造输入**（自动连招、无 CD 施法） | 输入包可被重放/篡改 | 输入包带帧号 + 时间戳 + 序号；服务器校验「输入是否合法」（CD、距离、资源、帧间隔） |
| **全图视野**（map hack） | 输入/事件包含隐藏信息，且客户端有完整状态 | 服务器做**视野裁剪**：只把与你有视野交集的事件/输入下发；或用状态同步 |
| **重放攻击** | 抓包重发旧输入 | 每帧输入带一次性序号 + 服务器侧窗口去重 |
| **加速齿轮** | 客户端自己决定执行速度 | 执行速度由输入到达驱动，服务器限速 |

**服务器回放校验**是最重要的一道闸：服务器用同一份模拟代码，从开局起按输入序列重放（或从定期快照继续），每 K 帧比对客户端上报的哈希。实践中它有两种强度：

- **完全重放**（每局从头跑）：能抓一切改状态的作弊，但服务器 CPU 成本 = 客户端成本，通常只能对排位/比赛开启。
- **抽样校验**（只校验部分帧/部分玩家）：成本可控，抓概率型作弊。

> 注意：影子模拟要求服务器的模拟代码与客户端**完全一致**（同版本、同定点库）。否则「服务器判定作弊」会变成误伤。

### 5.6 「卡」与「漂」的取舍

这是帧同步最核心的产品决策：

| 维度 | 「卡」（等帧，stall） | 「漂」（预测/追帧过快，drift） |
|---|---|---|
| 定义 | 输入没到齐，暂停推进 | 不等输入，先按预测执行，之后再对齐 |
| 体验 | 画面顿住，但状态**绝对正确** | 流畅，但可能出现「回拉/瞬移」 |
| 确定性 | 保持 | 需要回滚/校正，复杂度大增（第 6 章） |
| 常见选择 | 回合制、RTS、MOBA 对局内（可接受短暂停顿） | 格斗、动作类（不能顿） |

实务上多数项目在两者之间取平衡：**小落后用插值掩盖，中落后用追帧，大落后才等帧**。这就是 3.6 与 3.5 的组合策略。

## 6. 回滚网络 Rollback 与 GGPO

> **一句话结论**：Rollback 是帧同步的「实时化变体」——**先猜别人的输入把画面跑起来，收到真输入后回滚重放**，用 CPU 换延迟。

### 6.1 为什么需要回滚

纯帧同步必须等齐输入才能执行，格斗游戏 60Hz 下等 2 帧 = 33ms，加 RTT 动辄 100ms+，手感不可接受。Rollback 的思路是：**不等，先按「对方会重复上一帧输入」的假设跑**；等真输入到了，如果猜错，就把世界退回到那帧，用真输入重跑到当前帧。玩家看到的是「几乎无延迟的画面 + 偶尔一次极短的回拉」。

### 6.2 机制分解

```text
本地帧 f 执行：
1. 取本地输入 local(f)（已知）
2. 取远端输入 remote(f)：若已到达用真的；否则用「最后一帧已知输入」预测
3. step(f) → 保存状态快照 snapshot[f]
4. 若之后收到了 remote(f) 的真值且与预测不同：
   a. 回滚到 snapshot[f-1]（或更早的「已确认帧」）
   b. 用真 remote(f) 重放 f, f+1, ..., 当前帧（每帧都重新预测未确认的远端输入）
   c. 用重放后的状态继续渲染
```

| 概念 | 含义 |
|---|---|
| **回滚窗口**（rollback window） | 最多能回退多少帧，受内存与 CPU 限制，常见 7–10 帧 |
| **误预测率**（misprediction rate） | 猜错的帧占比；格斗游戏常见个位数百分比（经验量级） |
| **输入延迟帧**（input delay） | 可选的「人为延迟 N 帧」以减少误预测；N 越大越稳但越钝 |
| **状态快照** | 每帧一份可完整恢复的状态；必须能廉价复制与序列化 |

### 6.3 状态快照/序列化要求

Rollback 对状态结构的要求非常苛刻：

- **必须能廉价深拷贝**：不能有指针、`std::string`、`vector`、lambda；用固定大小数组 + 索引 + 内存池。
- **状态必须是 POD / 可 memcpy**：这样一帧快照就是一次 `memcpy`。
- **不能有隐藏的全局状态**：所有可变状态必须在「可快照的根对象」下。
- **不能依赖外部资源**（文件、网络、系统时间）。

```c
typedef struct {
    Unit units[MAX_UNITS];      // 固定大小
    uint32_t unit_count;
    Rng rng;                    // 随机数状态也要快照
    uint32_t frame;
} GameState;                    // 一帧快照 = sizeof(GameState) 字节

GameState snapshots[ROLLBACK_WINDOW + 1];   // 环形缓冲
```

### 6.4 性能模型

回滚的 CPU 成本近似：

```text
平均每帧成本 ≈ step_cost × (1 + mispredict_rate × avg_replay_frames)
avg_replay_frames ≈ min(rollback_window, RTT / Δt) / 2   （粗略量级）
```

例：60Hz（Δt≈16.7ms），RTT 80ms，则 `RTT/Δt ≈ 4.8` 帧，平均重放约 2–3 帧；若误预测率 10%，平均成本 ≈ `step_cost × 1.25`。若 RTT 200ms（≈12 帧），重放深度受窗口限制，成本显著上升。这就是为什么 rollback 主要用在**状态小、模拟快**的格斗/平台跳跃游戏，而不是大世界 MMO。

### 6.5 与帧同步的关系

| 维度 | 纯帧同步 | Rollback | 状态同步 |
|---|---|---|---|
| 同步对象 | 输入 | 输入 + 本地预测 | 状态 |
| 延迟来源 | 等输入 | 预测掩盖 | 预测 + 插值 |
| CPU 成本 | 1× | 1.2–2× | 客户端低、服务器高 |
| 画面回拉 | 无（会顿） | 有，但短 | 有（校正） |
| 状态可快照性 | 需要（断线/回放） | **强需求** | 不需要 |
| 典型用途 | RTS / MOBA 对局 | 格斗 / 平台跳跃 / 派对乱斗 | FPS / MMO / MOBA 表现层 |

一句话：**Rollback = 帧同步 + 预测 + 回滚重放**，三者共享同一套确定性模拟，区别只在「等不等输入」。

## 7. 状态同步原理

> **一句话结论**：状态同步是「服务器跑唯一一份真相，客户端是观众 + 预测器」——用带宽换一致性、可维护性和反作弊能力。

### 7.1 服务器权威与客户端角色

| 角色 | 服务器 | 客户端 |
|---|---|---|
| 世界状态 | 唯一真相源 | 本地副本，随时可被覆盖 |
| 输入 | 校验并应用 | 只上报意图，不直接生效 |
| 随机 | 服务器产生 | 只收结果（或种子） |
| 命中判定 | 服务器裁决 | 本地先表现，等确认 |
| 视角 | 知道全部 | 只知道服务器下发的部分（AOI） |

客户端做三件事：**表现**（把最近状态画出来）、**预测**（让自己的操作立刻有反馈）、**校正**（收到权威状态后把预测掰回来）。三者合起来就是「客户端是观众 + 预测器」。

### 7.2 进程结构

```text
         ┌──────────┐   长连接（WebSocket/TCP/KCP）   ┌────────────┐
客户端 ──►│ Gateway  │ ──────────────────────────────► │ 房间服/Room │
         │ 连接/鉴权 │ ◄──────────────────────────────  │  逻辑+广播  │
         └──────────┘        下发快照                 └─────┬──────┘
                                                           │ 匹配/数据
                                                     ┌─────▼──────┐
                                                     │ Matchmaker │
                                                     │  / DB / 缓存│
                                                     └────────────┘
```

常见实现的分层（不同团队叫法不同）：

| 层 | 职责 | 是否跑模拟 |
|---|---|---|
| **Gateway**（网关） | 连接管理、鉴权、限流、协议解包、会话路由 | 否 |
| **Room / 战斗服**（room/battle server） | 房间生命周期、权威模拟、快照生成与广播、结算 | **是** |
| **Matchmaker** | 匹配、组队、房间分配 | 否 |
| **持久化** | 玩家数据、背包、战绩 | 否 |

单房间的模拟通常是**单线程**的（避免锁与顺序不确定），一个进程跑几十到几百个房间。房间内实体多、CPU 吃紧时才考虑把模拟拆分（会引入一致性问题，第 12 章）。

### 7.3 快照模型：全量 / 增量 / 脏标记

| 模型 | 发送内容 | 带宽 | 实现复杂度 | 适用 |
|---|---|---|---|---|
| **全量快照**（full snapshot） | 所有可见实体的所有字段 | 最高 | 最低 | 实体少、快照率低、调试期 |
| **增量快照**（delta snapshot） | 与「客户端已确认的 baseline」相比有变化的字段 | 低 | 中 | 主流 |
| **脏标记**（dirty flags） | 服务器侧记录「本帧变了哪些实体」，只序列化这些 | 低 | 低–中 | 与增量配合 |
| **事件流**（events） | 只发「发生了什么」（开火、命中、死亡） | 最低 | 高（要求客户端能推演） | 表现层、特效、音效 |

工程上常见组合是：**状态用增量快照，表现用事件**。原因：状态保证「世界最终一致」，事件保证「动画/音效能精确触发」，两者职责不同。

```text
服务器 tick t：
  1. 应用本 tick 收到的输入
  2. 模拟（移动/技能/伤害）
  3. 标记脏实体
  4. 对每个客户端，按其 AOI 过滤可见实体
  5. 对每个客户端，与它的 baseline（已 ACK 的快照）做 delta
  6. 编码 + 发送
```

### 7.4 状态 vs 事件两种数据流

```text
状态流（快照）：每 50ms 一份「世界长什么样」，收不到就重发/等下一份
   → 幂等、可丢、可覆盖；适合连续量（位置、血量、朝向）

事件流：一次性「发生了什么」，丢了就永久丢失
   → 需要可靠传输（或在快照里带事件队列）；适合离散量（开火、命中、拾取）
```

| 维度 | 状态（snapshot） | 事件（event） |
|---|---|---|
| 语义 | 当前值 | 一次性通知 |
| 丢失后果 | 下一份快照覆盖，影响小 | 永久缺失，必须可靠或重放 |
| 频率 | 固定（如 20Hz） | 事件驱动 |
| 带宽特征 | 稳定、可预测 | 突发 |
| 典型内容 | 位置、速度、血量、buff 剩余时间 | 开火、命中、技能释放、掉落 |

### 7.5 完整时序

```text
客户端 C1                     服务器                          客户端 C2
   │  input(seq=100, 向前+开火)  │                                │
   ├───────────────────────────►│ 校验：CD/资源/距离/频率          │
   │                            │ 入队到 tick t 的输入             │
   │                            │ tick t：应用输入 → 模拟 → 判命中  │
   │                            │ 生成 snapshot(t)（含事件）       │
   │  snapshot(t) + ack(100)    │                                │
   │◄───────────────────────────┼───────────────────────────────►│
   │ 预测：本地早已转身、已播特效  │                                │ snapshot(t)
   │ 校正：位置误差 3cm → 平滑      │                                │ 插值 + 渲染
   │ 渲染                        │                                │
```

关键点：**客户端在收到 `snapshot(t)` 时，会同时知道「服务器确认了我的哪个输入」**（通过 ack / `last_processed_input_seq`）。这是预测校正的锚点（第 9 章）。

### 7.6 状态同步的三条铁律

1. **客户端永远不拥有状态的最终解释权**：本地改了也会被覆盖，所以「改客户端就无敌」的作弊思路在这里不成立（这是它相对帧同步的最大优势）。
2. **快照可以丢、可以合、可以跳**：客户端只需要「最新的一份」，中间的丢了无所谓；这与帧同步「必须每帧都到」形成鲜明对比。
3. **输入必须校验**：服务器不能盲信客户端上报的输入（CD、移动速度上限、频率、视野），否则「加速齿轮 + 自动瞄准」外挂照进不误。

## 8. 状态同步的序列化与带宽

> **一句话结论**：状态同步的带宽是「量化 × 位打包 × 增量 × 兴趣管理 × 优先级」五层挤出来的，每一层都能省一个数量级，但每一层都有精度或复杂度代价。

### 8.1 量化：把 float 换成 n bit 整数

核心公式：把连续量 `x ∈ [min, max]` 映射到 `n` 位整数：

```text
q = round((x - min) / (max - min) × (2^n - 1))
x' = min + q / (2^n - 1) × (max - min)
最大量化误差 = (max - min) / (2 × (2^n - 1))
```

| 量 | 范围 | 位宽 | 分辨率（步长） | 最大误差 |
|---|---|---|---|---|
| 地图内坐标 | 0–1000 m | 16 | `1000/65535 ≈ 1.53 cm` | 0.76 cm |
| 地图内坐标 | 0–4096 m | 16 | `6.25 cm` | 3.1 cm |
| 地图内坐标 | 0–1000 m | 17 | `0.76 cm` | 0.38 cm |
| 朝向角 | 0–360° | 16 | `0.0055°` | 0.0027° |
| 朝向角 | 0–360° | 12 | `0.088°` | 0.044° |
| 速度 | 0–100 m/s | 12 | `0.024 m/s` | 0.012 m/s |
| 血量 | 0–1000 | 10 | `0.98` | 0.49 |

三条估计原则：

- **精度按「视觉可辨」定**：FPS 里 1cm 的位置误差肉眼不可辨；但朝向 0.1° 的误差在远距离瞄准时会放大，所以角度常给 16 位。
- **相对坐标更省**：AOI 内实体相对玩家的偏移量范围小得多（如 ±64m），16 位就够到毫米级。
- **量化后的值是「权威值」**：服务器模拟用高精度，下发用量化值；客户端用同一量化值渲染，避免「服务器和客户端差一点」的抖动。

### 8.2 位打包与字节对齐

以「一名玩家实体的增量字段」为例（bit 布局示意）：

```text
bit  0        1        2        3        4-6      7
     │ 移动标志 │ 开火标志 │ 换弹标志 │ 蹲下   │ 武器ID │ 保留
bit  8-23     24-39        40-55        56-63
     │ pos.x 16 │ pos.y 16     │ yaw 16       │ 速度档 8 │
总计 8 字节（含 1 字节标志位 + 6 字节位置朝向 + 1 字节速度档）
```

| 编码方式 | 优点 | 缺点 |
|---|---|---|
| **字段对齐**（4/8 字节边界） | 实现简单、可直接 memcpy 结构体 | 浪费 padding，网络包变胖 |
| **位打包**（bit packing） | 极限省带宽 | 编解码代码繁琐、易错；C 结构体不能直接映射 |
| **变长整数**（varint / 7-bit） | 小数值只占 1 字节 | 大数值更费；需要边界处理 |
| **量化 + 位打包 + 增量** | 商用方案的标准组合 | 调试困难，需要工具支持（抓包解码器） |

位打包的两个工程提醒：

- **不要用「结构体直接 memcpy 发包」**：padding 字节内容不确定（未初始化），既泄露内存又导致包长/兼容性问题。要么显式序列化，要么 `#pragma pack` + 全部字段初始化。
- **位序 / 字节序要固定**：通常约定小端 + 低位先写，并在协议文档里写死，否则跨端（C++ 服务器 ↔ JS 客户端）解码会错位。

### 8.3 schema 驱动

手写序列化代码在字段一多就不可维护。schema 驱动 = 用接口定义（IDL）描述「有哪些实体、哪些字段、什么类型」，由工具生成编解码代码。

| 方案 | 形态 | 优点 | 代价 |
|---|---|---|---|
| **Colyseus Schema** | JS/TS 类 + 装饰器描述状态树，框架自动做增量和同步 | 上手极快，适合房间制小游戏 | 绑定框架；状态大时性能需关注 |
| **Protobuf** | `.proto` IDL，代码生成，可变长编码 | 生态成熟、跨语言、向后兼容 | 通用编码，**不针对游戏量化优化**；可变长让「位级别控制」变难 |
| **FlatBuffers** | 零拷贝反序列化，二进制 buffer 直接读 | 读快、适合大表/配置 | 写复杂、体积不是最小 |
| **自定义二进制协议** | 手写位打包 + 量化 | 带宽最优、延迟最低 | 维护成本高，需要自研工具链 |

> 通用原理：**schema 的价值在「单一事实来源 + 自动生成」，不在于某个具体格式**。游戏里常见做法是「自定义二进制 + 从 schema 生成代码」，兼顾带宽与可维护性。

### 8.4 delta 编码与 baseline ack

增量同步的核心是「基线」：客户端告诉服务器「我已经确认收到了到 `snapshot_id = S` 为止的状态」，服务器下次就以 `S` 为基线做差分。

```text
服务器为每个客户端维护 baseline_id
  客户端 ACK 收到 snapshot(S) → baseline_id = S
  下一次发送：diff(state(t), state(baseline_id))
  若 diff 太大（超过全量阈值）或客户端要求 → 直接发全量（keyframe）
```

三个必须处理的边界：

| 情况 | 后果 | 处理 |
|---|---|---|
| 客户端**丢包**导致 baseline 过旧 | diff 越来越大 | 服务器限制最大 delta 链长度；超过就发全量 |
| **baseline 指向的快照已从历史里淘汰** | 无法做 diff | 保存最近 K 份快照；淘汰前强制发全量 |
| **字段被多份 delta 依赖** | 一旦某帧丢失，后续全错 | 依赖链必须可重建：delta 是相对 baseline 的「绝对值差分」，不是相对上一帧的「增量叠加」 |

> 重要区别：**delta = 相对 baseline 的字段替换**（幂等，丢一帧只影响这一帧）；**incremental = 相对上一帧的增量累加**（不可丢，丢一帧永久错位）。状态同步几乎总是用前者。

### 8.5 兴趣管理 AOI

AOI（Area of Interest）= 只给客户端发「它应该看到的东西」。三种常见实现：

| 实现 | 原理 | 复杂度 | 适用 |
|---|---|---|---|
| **九宫格 / 网格**（grid） | 世界切格子，玩家只订阅周围 3×3 格 | 低，最常用 | MMO、SLG |
| **十字链表**（cross list） | 按 x/y 排序的链表，按坐标范围查 | 中 | 大量实体、移动频繁 |
| **四叉树 / BVH** | 空间分层索引 | 中高 | 稀疏大世界 |
| **视锥裁剪**（FPS） | 按相机朝向 + 视野角 + 距离 | 中 | 3D FPS |

AOI 的三个工程要点：

1. **进入/离开视野要有事件**：实体进入视野时客户端需要「出生」逻辑（播放入场、加载模型），离开时需要「销毁」。这些事件必须和快照一致。
2. **边界抖动**（AOI 边缘实体反复进出）会引发大量创建/销毁，常见做法是**加滞回带**（进入半径 < 离开半径）或降低检查频率。
3. **看不到 ≠ 不存在**：服务器仍然模拟全部实体，只是不下发。因此 AOI 也是反作弊手段（第 5 章）。

### 8.6 优先级与带宽预算

带宽不够时，不能平均分配，要按「对玩家的价值」排序发送：

```text
优先级 ≈ 距离权重 × 视野权重 × 变化幅度 × 实体重要性
例如：正在交火的敌人 > 视野内移动的队友 > 远处静止的小兵
```

预算控制常见做法：

| 手段 | 说明 |
|---|---|
| **每客户端字节预算**（如 8–16 KB/s） | 超预算就降频/降精度/裁剪远处实体 |
| **自适应快照率** | 拥塞时 20Hz → 10Hz，恢复后再升 |
| **分级 LOD** | 远处实体只发位置，近处才发完整状态 |
| **关键帧兜底** | 预算超限或长时间未同步时发全量 |

**带宽算例**（假设，用于量级感受）：20 人对局，AOI 内平均 10 个实体可见，每实体增量 12 字节，快照 20Hz：

```text
单客户端下行 ≈ 10 × 12 × 20 = 2400 B/s ≈ 2.4 KB/s ≈ 19 kbps
服务器上行 ≈ 20 × 2.4 KB/s = 48 KB/s ≈ 0.4 Mbps（单房间）
```

对比帧同步：4 人房 20Hz，每帧输入集合约 4×8=32B，加冗余 ×3 与协议头 ≈ 150B/帧：

```text
单客户端下行 ≈ 150 × 20 = 3000 B/s ≈ 3 KB/s
```

量级上两者接近——**帧同步省的是「实体数」，状态同步省的是「玩家数」**。1000 个小兵时帧同步仍是 3KB/s，状态同步会爆炸；100 个玩家大乱斗时状态同步靠 AOI 摊薄，帧同步则要为每人传输入。

## 9. 客户端预测与服务器校正

> **一句话结论**：预测让「自己的操作」立刻有反馈，校正让「世界的真相」最终归位；实现的关键是**给每个输入编号、记住自己预测了什么、收到权威状态后重演**。

### 9.1 为什么必须预测

状态同步下，如果玩家按下「前进」后老老实实等服务器回快照，那么从按键到看见移动的延迟是：

```text
L = 上行 RTT/2 + 服务器 tick 等待 + 下行 RTT/2 ≈ RTT + Δt_tick
RTT 80ms + 20Hz tick 50ms ≈ 130 ms
```

超过约 100ms 的「输入→反馈」延迟，人就能明显感到「黏」。更要命的是**不对称**：别人的动作有 100ms 插值延迟（第 10 章），自己的动作也有 130ms，操作类游戏直接没法玩。预测把这个数压到接近 0（本地立即执行），代价是偶尔要「被校正」。

### 9.2 输入序列号与 ack

```text
客户端：input_seq 从 0 自增，每个上行输入带 (seq, 本帧的意图)
服务器：处理到第 N 个输入后，在快照里带 last_acked_input = N
客户端：收到快照 → 知道自己哪一段预测已被服务器确认
```

两条纪律：

- **入队与确认必须一一对应**：客户端保存「已发送但未确认」的输入队列（pending inputs）。收到 ack 后，从队列里删掉 `seq ≤ ack` 的项。
- **服务器必须按 seq 顺序应用**（或至少按序记录），否则「确认到 N」就没有意义。UDP 上乱序到达的输入，常见做法是缓冲一个短窗口后按序处理，或在快照里回滚（成本高，少用）。

### 9.3 本地预测 + 收权威快照后 rewind/replay

```python
# 客户端主循环
def on_local_input(intent):
    seq = next_seq()
    pending.append((seq, intent))          # 记住预测依据
    predict(intent)                        # 立即本地生效：转身、起步、开火特效
    net.send_input(seq, intent)            # 上行

def on_snapshot(snap):                     # 收到权威快照
    ack = snap.last_acked_input
    # 1. 丢弃已被确认的输入
    pending[:] = [(s, i) for (s, i) in pending if s > ack]
    # 2. 用权威状态覆盖本地（含位置、速度、状态机、血量）
    local = from_snapshot(snap)
    # 3. 把「服务器还没处理的、我已预测过的输入」重新应用一遍
    for seq, intent in pending:
        local = apply(local, intent, dt_tick)
    # 4. 误差平滑：把「重演后的位置」与「刚才显示的位置」之间做视觉过渡
    smooth.begin(visual_pos, local.pos, duration_ms=120)
```

三个容易写错的地方：

- **重演必须用「固定 tick 的 apply」**，而不是「按本地帧间隔跑物理」，否则重演结果与服务器不一致。
- **重演的输入必须是一个完整的「服务器语义」序列**：如果服务器对输入有额外效果（比如自动面向、后坐力），客户端重演也要包含，否则误差会越来越大。最好的办法是**客户端与服务器共享同一份移动/状态机代码**。
- **不要用「最新快照 + 最新输入」直接覆盖**就完事：中间未确认的输入如果没有重演，你每帧都会把玩家往回拉，形成「橡皮筋」。

### 9.4 误差平滑：视觉上别跳

校正有三种策略，按「误差大小」选择：

| 策略 | 触发条件 | 做法 | 观感 |
|---|---|---|---|
| **瞬移**（snap / teleport） | 误差 > 阈值（如 1–2 m，或被击退/传送） | 直接把渲染位置设为权威位置 | 明显跳变，但「诚实」 |
| **平滑**（smooth / blend） | 误差中等（几 cm 到 1 m） | 渲染位置在 50–200ms 内插值到真值 | 几乎无感 |
| **速度修正**（velocity correction） | 误差小、持续存在 | 不直接改位置，而是把误差折算成附加速度，逐步抵消 | 最自然，但收敛慢 |

```python
# 指数衰减式平滑：每帧把剩余误差缩小固定比例
def smooth_step(visual, target, dt, tau_ms=100):
    k = 1 - math.exp(-dt / (tau_ms / 1000.0))   # 与帧率无关
    visual.pos = lerp(visual.pos, target.pos, k)
```

工程经验（经验量级）：

- 平滑窗口 **100–200ms** 是常见区间；太短会看到「抽一下」，太长会让人觉得角色「在冰上滑」。
- 位置误差与速度误差要**分开处理**：位置平滑不要破坏速度，否则会与服务器速度打架，产生持续偏移。
- 对「不可接受的误差」（穿墙、掉下地图）必须直接 snap，不能温和处理。

### 9.5 三种校正策略的信任边界

| 内容 | 客户端可预测 | 客户端可裁决 | 说明 |
|---|---|---|---|
| 移动、朝向、动画 | 是 | 否 | 预测无害，错了平滑即可 |
| 技能冷却、资源消耗 | 是（乐观） | 否 | 预测失败要把技能「退回」（回滚 UI 与逻辑） |
| 命中、伤害、死亡 | 可表现 | **否** | 必须等服务器 |
| 拾取、金钱、经验 | 否 | 否 | 只信服务器 |
| 位置碰撞（穿墙） | 是（本地先挡） | 否 | 服务器最终裁决 |

一句话：**能预测的是「表现」，不能预测的是「资产与胜负」**。

## 10. 插值、外推与命中判定

> **一句话结论**：插值用「延迟」换「平滑」——为了让别人的动作看起来顺，客户端要故意把渲染时间往回退 100–200ms；延迟补偿则让服务器在命中判定时「回到过去」。

### 10.1 为什么需要插值

服务器 20Hz 发快照（每 50ms 一份），客户端 144Hz 渲染。如果直接把最新快照画出来，会看到：

- 动作以 20Hz 跳跃（每 50ms 才动一次）。
- 一旦某份快照晚到 30ms，画面就卡一下。

解决办法：**渲染「过去」**。客户端维护一个快照缓冲，把渲染时刻定在「最新快照时间 - 延迟」，在相邻两份快照之间插值。

```text
服务器快照：   S(t0)        S(t1)        S(t2)        S(t3)
时间轴：       |             |             |             |
渲染时刻：            ↑ now - D  （D ≈ 100–200ms，落在 S(t1)..S(t2) 之间）
插值：        在 S(t1) 与 S(t2) 之间按比例线性插值
```

### 10.2 渲染延迟 D 的推导

要让插值永远有「下一份快照」可用，缓冲必须覆盖：

```text
D ≥ 快照间隔 T_snap            # 至少落后一份，才能在 S(t1) 与 S(t2) 之间插值
  + 网络抖动 jitter            # 最坏情况下快照晚到
  + 服务器 tick 排队
```

例：`T_snap = 50ms`（20Hz），抖动 ±30ms，则 `D ≈ 80–100ms`；再留一份余量（防止连续两次晚到）就是 **100–150ms**。若快照率只有 10Hz（T=100ms），`D` 自然升到 150–250ms。这解释了两件事：

1. **为什么「约 100–200ms 的渲染延迟」是常态**：它不是拍脑袋，而是「快照间隔 + 抖动余量」的必然结果。
2. **为什么高竞技 FPS 要提高快照率**：快照率翻倍，插值延迟就能砍掉一半左右。

> 经验量级：FPS 常见快照率 20–30Hz，插值延迟 1–3 个快照间隔；MOBA 常见 10–20Hz 快照 + 100ms 级延迟。

### 10.3 插值类型

| 类型 | 公式/做法 | 平滑度 | 代价 |
|---|---|---|---|
| **线性插值**（lerp） | `p = p0 + (p1-p0) × t` | 位置连续、速度不连续（拐角会「折一下」） | 最低 |
| **Hermite / 三次样条** | 用前后各一份快照估计速度，做三次插值 | 速度也连续，转向顺滑 | 需要更多样本 |
| **球面插值**（slerp） | 朝向用四元数插值 | 旋转自然 | 需要四元数 |
| **外推**（extrapolation） | 用最后两份快照的速度「猜未来」 | 丢包时也不卡 | 猜错会「穿墙/回拉」 |

```python
def sample(buffer, render_time):
    i = find_segment(buffer, render_time)      # 找到 t_i <= render_time < t_{i+1}
    if i is None: return None
    a, b = buffer[i], buffer[i + 1]
    t = (render_time - a.time) / (b.time - a.time)   # 0..1
    return lerp_state(a, b, t)
```

### 10.4 外推与橡皮筋

当渲染时间已经追上最新快照（`render_time > last_snapshot.time`），三种处理：

| 方案 | 行为 | 后果 |
|---|---|---|
| **冻结** | 停在最后一份快照 | 卡顿感明显，但不会错 |
| **外推** | 按最后已知速度/角速度继续推 | 平滑，但会「猜错」 |
| **减速** | 逐渐放慢直到停下 | 折中，常用于「等下一份快照」 |

外推的经典翻车场景：玩家撞墙。客户端按速度外推 → 角色穿进墙里 → 下一份权威快照把它拉回来 → 这就是「橡皮筋」（rubber-banding）。缓解：

- **只对「可预测的运动」外推**（匀速直线），不对外推碰撞/技能。
- 设置**最大外推时间**（如 150ms），超时冻结。
- 外推时用**服务器下发的最小碰撞信息**（如 AOI 内的障碍）做局部约束。

### 10.5 延迟补偿（lag compensation）

FPS 的核心难题：玩家看到的是 100ms 前的世界，他对着「看到的目标」开枪，但服务器上的目标已经移动了。若不补偿，玩家必须「打提前量」，手感极差。

**做法：服务器在判定命中时，把世界回退到「该玩家看到的世界」的那一刻。**

```python
def resolve_hit(shooter, shot, client_render_time):
    # 1. 计算玩家看到的那一刻：服务器时间 - (RTT/2 + 插值延迟)
    rewind_to = client_render_time
    # 2. 把目标位置回退到 rewind_to（用服务器保存的历史位置）
    for target in candidates(shot):
        pos_then = target.history.sample(rewind_to)
        if ray_hits(shot, pos_then):
            return hit(target)
    return miss()
```

要求与边界：

| 要素 | 说明 |
|---|---|
| **历史位置缓冲** | 服务器需保留每个实体过去 ~1s 的位置（常见 1–2s，取决于最大补偿窗口） |
| **补偿窗口上限** | 常见 200–300ms；超过不补偿（防止高延迟玩家获得过大优势） |
| **补偿量 = RTT/2 + 客户端插值延迟** | 只回退「玩家看到的那一帧」，不是无脑回退 RTT |
| **作弊边界** | 玩家可伪造延迟（lag switch）获得「打过去的位置」优势 → 服务器限制补偿上限 + 检测异常 RTT 抖动 |
| **服务器仍要校验射线** | 回退的只是目标位置，射线本身与弹药/射速必须服务器裁决 |

### 10.6 两种「作弊式优势」的对称性

延迟补偿有一个常被忽略的事实：**它让高延迟玩家「打旧位置」命中，也让低延迟玩家「打新位置」更准**。所以补偿窗口的选择本质是在玩家之间分配公平性：

- 窗口大：高延迟玩家手感好，低延迟玩家觉得「我明明打中了却没中」（其实他打的是旧位置）。
- 窗口小：高延迟玩家必须自己提前量，体验差。

常见折中：**窗口 = 200ms 左右 + 对延迟异常玩家做惩罚/不补偿**。

## 11. 对比矩阵与选型

> **一句话结论**：选型不是选「哪个更好」，而是回答「我的游戏更怕带宽爆炸、更怕作弊、还是更怕手感差」——这三者的答案直接决定架构。

### 11.1 12 维对比矩阵

| 维度 | 帧同步 | 状态同步 | 混合（战斗帧同步 + 外围状态同步） |
|---|---|---|---|
| **带宽** | 极低，∝ 玩家数 × 输入帧率；1000 单位也不涨 | 中高，∝ 可见实体数 × 快照率（AOI 可摊薄） | 低（战斗内）+ 中（大厅/背包） |
| **CPU 成本** | 客户端高（所有实体本地算）、服务器低（归并/转发，开影子校验后升高） | 客户端低（只算表现与预测）、服务器高（唯一模拟 + AOI/delta） | 中，双端都要付 |
| **作弊难度** | 高（输入公开、本地算状态，靠服务器回放校验） | 低（服务器权威，客户端改不了结果） | 中（战斗内取决于校验强度） |
| **回放** | 极便宜（= 输入序列，几 KB） | 贵（要录状态流或事件流，MB 级） | 便宜（战斗段） |
| **断线重连** | 难（要快照 + 追帧 + 输入补齐） | 容易（重连后直接收最新全量快照） | 难 |
| **跨端一致性** | 难（确定性要求跨平台/跨编译器） | 容易（只有服务器算，客户端只表现） | 难 |
| **开发成本** | 高（确定性工程 + 容错 + 反作弊） | 中（预测/插值/带宽优化） | 最高（两套都要） |
| **状态规模** | 无上限（本地算，不传输） | 受 AOI 与带宽约束（同屏实体数有限） | 战斗部分可控 |
| **随机性** | 必须确定性随机（种子同步） | 服务器随机，客户端只收结果 | 战斗内确定性，外围服务器随机 |
| **物理** | 需要可确定性物理（3D 难，2D 可行） | 任意物理（只在服务器算） | 战斗内用简化确定性物理 |
| **AI** | 必须确定性（同输入同决策）；常用确定性行为树/固定点 | 服务器跑 AI，客户端只表现 | 战斗 AI 确定性，其余服务器 |
| **调试难度** | 高（desync 极难复现定位） | 中（状态可观测、可回放） | 高 |

把 12 维压成三句话：

1. **怕带宽 / 实体多 / 要回放** → 帧同步。
2. **怕作弊 / 状态大 / 要易维护** → 状态同步。
3. **既要又要** → 混合，但准备好付「两套复杂度」。

### 11.2 决策树

```text
Q1 游戏是「同时操作、毫秒级对抗」吗（FPS / 动作 / 格斗）？
├── 是 → 状态同步（服务器权威 + 预测 + 延迟补偿）
│         └── 但若是 1v1 格斗/平台跳跃、状态小 → 可考虑 Rollback（帧同步变体）
└── 否 ↓
Q2 同屏实体数是否很大（>100）并且需要长期一致（RTS / 大规模团战）？
├── 是 → 帧同步（或「帧同步逻辑 + 状态同步表现」的混合）
└── 否 ↓
Q3 作弊是否会直接毁掉经济系统（卡牌 / 抽奖 / 排位）？
├── 是 → 状态同步（服务器裁决一切随机与结算）
└── 否 ↓
Q4 是否需要精确回放 / 观战 / 录像分析（电竞、赛事）？
├── 是 → 帧同步（回放 = 输入）
└── 否 ↓
Q5 团队是否有确定性工程能力（定点库、跨端验证、desync 排查工具链）？
├── 有 → 帧同步
└── 没有 → 状态同步（先用最朴素的全量快照跑通，再优化）
```

> 决策树的真正用法：**从 Q1 往下走，第一个「是」就是答案**；走到底还没中，选状态同步（它的下限最高）。

### 11.3 六类游戏案例

| 类型 | 常见选择 | 为什么 | 反向选择的代价 |
|---|---|---|---|
| **MOBA**（5v5 推塔） | 状态同步为主（服务器权威 + 客户端预测）；部分移动端产品用帧同步 + 服务器校验 | 单位数适中（几十），需要强反作弊与断线重连；玩家对「自己操作跟手」极敏感 | 纯帧同步：一个人卡全队等、作弊面大、断线重连复杂 |
| **FPS**（射击） | 状态同步 + 预测 + 延迟补偿 | 毫秒级命中判定必须服务器权威；3D 物理/浮点难以跨端确定；需要视野裁剪防透视 | 帧同步：延迟不可接受、确定性几乎不可能、全图信息泄露 |
| **RTS**（星际/帝国类） | 帧同步（经典选择） | 单位成百上千，状态同步带宽爆炸；回放便宜；操作节奏容忍 100ms 级延迟 | 状态同步：同屏几百单位 × 20Hz 快照，带宽与 CPU 都难扛 |
| **MMO**（大世界） | 状态同步 + AOI（常基于 TCP 或可靠 UDP） | 玩家海量、持久世界、服务器必须权威；用 AOI 把带宽摊薄 | 帧同步：世界状态巨大、玩家间不同步、断线重连地狱 |
| **卡牌 / 回合制** | 状态同步（服务器裁决随机）+ 低频快照 | 延迟不敏感；作弊直接影响经济；回合边界天然是同步点 | 帧同步：毫无收益，反而引入确定性负担 |
| **派对休闲**（多人乱斗/物理沙盒） | 视物理复杂度：轻量 2D → 帧同步/rollback；重 3D 物理 → 状态同步（客户端表现 + 服务器宽松校验） | 物理确定性是分水岭；休闲游戏对「偶尔不同步」容忍度高 | 重物理强行帧同步：跨端 desync 会持续烧人 |

对「MOBA 为什么不用纯帧同步」补一句：公开的技术分享里两种做法都能找到成功案例，差别在**产品对作弊与断线体验的容忍度**，以及团队是否愿意维护确定性工具链——这是工程选择，不是理论优劣。

### 11.4 混合架构：战斗帧同步 + 大厅状态同步

```text
┌───────────────────────────────────────────────┐
│ 大厅 / 匹配 / 背包 / 商店 / 聊天                │  ← 状态同步（HTTP/WS，服务器权威）
├───────────────────────────────────────────────┤
│ 战斗对局（小房间，固定 2–10 人）                │  ← 帧同步（输入广播 + 确定性模拟）
│   ├─ 战斗结束 → 上报结果 → 服务器校验/结算       │
│   └─ 战斗录像 = 输入序列                        │
└───────────────────────────────────────────────┘
```

混合架构的三个接口必须设计好：

1. **结算校验**：战斗结果不能由客户端说了算。服务器用影子模拟回放输入，或至少做合理性校验（局时长、伤害上限、资源变化）。
2. **状态交接**：进入战斗时的初始状态（英雄属性、装备、buff）必须由服务器生成并下发给所有客户端，且**逐位一致**（序列化要定点化）。
3. **断线与重连**：战斗内断线走帧同步快照，跨战斗断线走大厅重连。

### 11.5 选型时最容易被忽略的三个成本

| 成本 | 说明 |
|---|---|
| **确定性工具链** | 帧同步需要：定点数学库、跨端一致性 CI、哈希监控、desync 复现器、回放器。这些是「一次性投入 + 长期维护」 |
| **网络仿真** | 状态同步需要：延迟/丢包/抖动注入、弱网测试、带宽预算监控。没有这些，上线必炸 |
| **回放与观战** | 帧同步几乎免费，状态同步要专门设计；如果产品要做赛事/教学，这一项权重很高 |

## 12. 服务端架构与工程落地

> **一句话结论**：同步算法的优雅会被工程细节吃掉——**房间模型、容量估算、监控指标**这三件事决定你能不能上线。

### 12.1 房间服 / 战斗服进程模型

```text
进程：match-server（无状态，可水平扩展）
  └─ 匹配队列 → 分配房间 → 通知 gateway
进程：room-server（有状态，一个进程跑 N 个房间）
  ├─ room #1：状态机 room_fsm（等待/加载/战斗/结算）
  ├─ room #2
  └─ ...
进程：gateway（无状态，长连接）
  └─ 维持 WS/KCP 连接，转发到 room-server
```

| 模型 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **单房间单线程** | 房间内所有逻辑在一个线程/事件循环里顺序执行 | 无锁、顺序确定、易调试 | 单核上限，房间不能太大 |
| **单房间多线程** | 模拟并行（物理、AI 分线程） | 单房间吞吐高 | 归约顺序不确定 → 帧同步不可用、状态同步要小心 |
| **分片**（shard） | 大世界按区域切分，不同进程负责 | 可扩展 | 跨片交互（传送、跨区战斗）复杂 |

> 帧同步房间**强烈建议单线程**：确定性要求顺序固定。状态同步房间可以多线程，但「同一实体的更新顺序」必须固定。

### 12.2 状态持久化与回放归档

| 内容 | 存储 | 频率 | 说明 |
|---|---|---|---|
| 玩家资产/背包 | 关系库 + 缓存 | 落库（事务） | 必须强一致，走事务 |
| 对局结果 | 关系库 | 结算时 | 幂等写入（防重复结算） |
| 战斗回放 | 对象存储 / 列存 | 对局结束 | 帧同步存输入序列（KB 级），状态同步存关键帧或事件流（MB 级） |
| 遥测/日志 | 列存 / 日志系统 | 异步 | 用于 desync 分析与监控 |

回放归档的两个工程点：

- **版本标记**：回放必须记录客户端版本、逻辑版本、地图/规则版本，否则无法复现。
- **隐私与容量**：回放保留期要按产品定（常见 7–90 天）；状态同步回放体积大，常见做法是「只存关键帧 + 事件，按需重算」。

### 12.3 容量估算算例

**帧同步房间**（10 人，20Hz，输入冗余 ×3）：

```text
每帧输入集合：10 玩家 × 8 B = 80 B
带冗余的广播包：约 240 B + 协议头 60 B ≈ 300 B
服务器出向：300 B × 20 Hz = 6 KB/s per 客户端
            × 10 客户端 = 60 KB/s ≈ 0.5 Mbps per 房间
1000 房间 ≈ 60 MB/s ≈ 480 Mbps（出向）
CPU：主要是归并与转发，单房间很轻；开影子校验后 ≈ 10 倍客户端模拟成本
```

**状态同步房间**（20 人，20Hz，AOI 内 10 实体 × 12 B 增量）：

```text
单客户端下行：10 × 12 × 20 = 2.4 KB/s
房间出向：2.4 KB/s × 20 = 48 KB/s ≈ 0.4 Mbps
服务器 CPU：每 tick 要模拟 20 人 + AOI 过滤 + 20 份 delta 编码
```

> 以上都是**量级估算**，真实值取决于协议头、加密、可靠性层、拥塞状态与 AOI 命中率。做容量规划时必须用压测脚本注入真实网络条件，别拿公式当结论。

### 12.4 监控指标

| 指标 | 定义 | 健康阈值（经验量级） | 异常时的排查方向 |
|---|---|---|---|
| **帧耗时** | `step()` 单帧耗时 p50/p99 | p99 < 单帧预算的 50% | 逻辑热点、GC、锁竞争 |
| **掉帧/超时** | 单帧耗时超过 Δt 的次数 | 接近 0 | 同上 |
| **desync 率** | 哈希不一致的对局占比 | 目标 0；>0.1% 需告警 | 4.11 的六步排查 |
| **RTT 分布** | p50 / p95 / p99 | p99 与 p50 差距 <2–3 倍 | 接入网、路由、服务器位置 |
| **丢包率** | 上行/下行丢包 | <1% 正常；>3% 影响体验 | 网络质量、MTU、无线 |
| **输入等待帧数** | 等帧时平均等待帧数 | <1 帧 | 玩家网络、冗余帧数量、提前量 |
| **快照大小** | 每客户端每快照字节数 | 在预算内（如 8–16 KB/s） | 量化、AOI、delta 链 |
| **回滚次数/帧** | rollback 触发频率 | 与误预测率一致 | 预测策略、输入延迟设置 |
| **重连成功率** | 断线后成功恢复到对局的比例 | >95% | 快照、追帧、超时设置 |

监控的最小闭环是：**指标异常 → 定位到房间/玩家/版本 → 有回放或输入日志可复现 → 有 fix 与回归验证**。没有回放/日志的团队只能猜。

## 13. 代码走读：从开源项目学什么

> **一句话结论**：不要通读源码——**带着「输入缓冲 / 帧循环 / 校验和 / 快照 / 预测」这五个问题去定位代码**，读 300 行就够。

### 13.1 帧同步项目读哪几处

| 目标 | 找什么 | 读到什么程度 |
|---|---|---|
| **输入结构** | `Input` / `Command` / `FrameInput` 类型定义；序列化函数 | 字段有哪些、怎么量化、带不带帧号 |
| **帧循环** | 主循环 / `update(frame)` / `Tick` | 帧推进条件（等输入？定时器？）、追帧逻辑 |
| **输入缓冲** | `FrameBuffer` / `inputQueue` / `receiveInput` | 去重、乱序处理、超时托管 |
| **确定性模拟** | 定点类型、数学库、随机数 | 是否全整数、有无 `sin/cos` 浮点 |
| **校验和** | `checksum` / `hash` / `verify` 关键字 | 哈希什么、多久一次、不一致怎么办 |
| **快照/重连** | `serialize` / `snapshot` / `saveState` | 快照粒度、恢复流程 |

### 13.2 状态同步项目读哪几处

| 目标 | 找什么 | 读到什么程度 |
|---|---|---|
| **状态定义（schema）** | 状态类 / `.proto` / schema 装饰器 | 字段类型、量化、是否增量 |
| **快照/增量** | `snapshot` / `delta` / `encode` / `ack` | baseline 怎么维护、全量何时发 |
| **AOI** | `interest` / `view` / `grid` / `radius` | 实体可见性判定、进出视野事件 |
| **预测与校正** | `predict` / `reconcile` / `rewind` / `pendingInputs` | 输入队列、重演、平滑 |
| **插值** | `interpolate` / `buffer` / `renderTime` | 缓冲深度、外推策略 |
| **延迟补偿** | `lagCompensation` / `history` / `rewind` | 回退时刻怎么算、窗口多大 |

### 13.3 读源码五步法

1. **先读协议/数据定义**（10 分钟）：消息类型、字段、序列化。协议是架构的「目录」。
2. **再找主循环**（15 分钟）：所有网络游戏都有一个 `while (running) { tick(); }`。从它出发画出「输入 → 模拟 → 广播」的调用链。
3. **沿着一条消息走完整路径**（30 分钟）：挑一条「玩家移动」，从采集到对方渲染，逐层打日志或断点。
4. **对照本文档验证**（30 分钟）：它有没有冗余帧？有没有追帧？哈希怎么算？和本文哪一节对得上、哪一节它偷懒了？
5. **改一个小功能**（1–2 小时）：加一个字段（如「蹲下」）、加一个校验、加一个 AOI 半径配置。能改通说明你真读懂了。

<details>
<summary>Q1 ★ 帧同步为什么怕浮点？</summary>

严格说不是「浮点本身不确定」：IEEE 754 的加减乘除开方是正确舍入的，同输入同架构结果逐位相同。怕的是**超越函数（sin/cos/pow）在不同 libm 实现里差最后 1 ulp**、编译器把 `a*b+c` 收缩成 FMA 或反过来、`-ffast-math` 允许重排、x87 80 位中间精度、跨架构的 denormal 处理差异——这些都会让同一份逻辑在不同端算出不同结果，几百帧后分叉。对策是模拟层全定点/整数，数学函数自研（查表 + 插值、CORDIC）。

</details>

<a id="q2"></a>
<details>
<summary>Q2 ★ Q16.16 的乘法和除法怎么实现？溢出边界在哪？</summary>

乘法：`(int64)a*b >> 16`（加 `0x8000` 做舍入）；`|a*b|` 最大约 `2^62`，int64 装得下，但结果若超出 ±32767.99 仍会截断，例如 `200 × 200 = 40000`。除法：`((int64)a << 16) / b`，先判 `b == 0`，再判结果是否超出 int32；等价溢出条件 `|a| ≥ |b| × 32768`，典型触发是除以小于 1 的数。开方用整数逐位开方或固定次数牛顿迭代（次数固定才确定）。

</details>

<a id="q3"></a>
<details>
<summary>Q3 ★ 冗余帧是什么？为什么需要？</summary>

每个输入包携带最近 N 帧的输入记录（常见 N=3–10）。UDP 会丢包，而帧同步少一条输入那一帧就永远算不出，全房间等帧；冗余帧让「丢一包」不等于「丢一帧」，接收方按帧号去重即可。也可以用「同一帧重发 M 次」，实现更简单但抗连续丢包差。

</details>

<a id="q4"></a>
<details>
<summary>Q4 ★ 追帧（catch-up）怎么做？注意什么？</summary>

本地帧号落后服务器超过阈值时，连续执行 `step()` 直到追上，中间帧不渲染，并用单帧时间预算（如 8ms）限制每次最多追多少帧，避免主线程卡死。注意：追帧期间关闭渲染插值；追帧有上限并分多帧完成；追帧是「往后执行已知帧」，回滚是「退回旧状态重跑」，两者不同。

</details>

<a id="q5"></a>
<details>
<summary>Q5 ★ 断线重连的快照从哪来？</summary>

服务器维护「定期快照（每 N 帧或关键节点）+ 之后的输入序列」。重连时把 `frame = f_snap` 的完整状态（实体、随机数状态、ID 分配器、计时器、待处理事件）下发，再补发从 `f_snap` 到当前的输入，客户端从 `f_snap` 追帧到当前。快照必须包含一切影响后续模拟的状态，否则追出来的状态也是错的。

</details>

<a id="q6"></a>
<details>
<summary>Q6 ★ 服务器回放校验怎么防作弊？</summary>

服务器用与客户端**同版本**的确定性模拟，按输入序列跑影子模拟，每 K 帧比对客户端上报的状态哈希；不一致即判分叉/作弊。强度分两档：完全重放（抓一切改状态，CPU 成本高，排位/比赛开启）与抽样校验（成本可控）。前提是服务器与客户端模拟代码完全一致，否则误伤。

</details>

<a id="q7"></a>
<details>
<summary>Q7 ★ Rollback 的原理与成本？</summary>

先按「远端会重复上一帧输入」的假设本地执行并保存每帧快照；真输入到达后若与预测不同，回滚到旧快照、用真输入重放到当前帧。成本 ≈ `step_cost × (1 + 误预测率 × 平均重放帧数)`，平均重放帧数约 `min(窗口, RTT/Δt)/2`。要求状态可廉价深拷贝（POD、无指针）、每帧快照，窗口常见 7–10 帧，用于格斗/动作类。

</details>

<a id="q8"></a>
<details>
<summary>Q8 ★ 全量快照、增量、脏标记有什么区别？</summary>

全量：发所有可见实体所有字段，带宽最高、实现最简单。脏标记：服务器记录「本帧哪些实体变了」，只序列化这些。增量（delta）：把「当前状态」与客户端已确认的 baseline 做字段级差分，只发变化字段。主流组合是「脏标记筛实体 + 相对 baseline 的 delta 字段 + 超限发全量兜底」。注意 delta 是相对 baseline 的**绝对字段替换**（幂等），不是相对上一帧的累加（丢一帧就永久错位）。

</details>

<a id="q9"></a>
<details>
<summary>Q9 ★ 位打包与量化的误差怎么算？</summary>

把 `x ∈ [min,max]` 映射到 n 位：`q = round((x-min)/(max-min) × (2^n-1))`，最大误差 `(max-min)/(2(2^n-1))`。例：0–1000m 用 16 位，步长约 1.53cm、误差 0.76cm；角度 16 位误差 0.0027°。位打包就是把多个量化字段按 bit 拼接（如 8 字节装下位置+朝向+速度档），注意不能用结构体直接 memcpy（padding 未初始化）且位序/字节序要写死。

</details>

<a id="q10"></a>
<details>
<summary>Q10 ★ AOI（兴趣管理）怎么做？</summary>

只给客户端下发它「应该看到」的实体。常见实现：九宫格/网格（最常用）、十字链表、四叉树/BVH、FPS 的视锥裁剪。工程要点：进出视野要有事件（客户端据此创建/销毁实体）、边界要加滞回带防抖动、服务器仍模拟全部实体（AOI 也是反作弊手段）。

</details>

<a id="q11"></a>
<details>
<summary>Q11 ★ 延迟补偿（lag compensation）是什么？</summary>

FPS 里玩家看到的是 100ms 前的世界，对着「看到的目标」开枪，服务器上的目标已经移动。做法是服务器保存每实体过去约 1s 的位置历史，判定命中时把目标回退到「玩家看到的那一刻」——回退量 ≈ `RTT/2 + 客户端插值延迟`，上限常见 200–300ms。射线、弹药、射速仍由服务器裁决；补偿窗口过大对低延迟玩家不公平，也给了 lag switch 作弊空间。

</details>

<a id="q12"></a>
<details>
<summary>Q12 ★ MOBA 为什么主流用状态同步？</summary>

单位数适中（几十），状态同步带宽可接受；最关键是**自己操作必须跟手**（本地预测把反馈延迟压到接近 0）和**反作弊**（服务器权威，客户端改不了结果）；断线重连也简单（重连收全量快照）。纯帧同步的代价是「一个人卡全队等」、作弊面大、重连要追帧。也有移动端产品用帧同步 + 服务器校验，属于工程权衡而非理论优劣。

</details>

<a id="q13"></a>
<details>
<summary>Q13 ★ 为什么 RTS 用帧同步？</summary>

同屏单位成百上千，状态同步要传的状态量与带宽会爆炸，而帧同步只传几个玩家的点击，带宽与实体数解耦；RTS 操作节奏容忍 100ms 级输入延迟（不像 FPS）；回放 = 输入序列，几 KB 就能存整局，赛事/复盘成本极低。代价是要保证确定性（2D、实体多但逻辑简单，比 3D 物理可行）。

</details>

<a id="q14"></a>
<details>
<summary>Q14 ★ 为什么 FPS 不用帧同步？</summary>

三个硬伤：① 毫秒级对抗不能等输入凑齐，帧同步的输入延迟不可接受；② 3D 物理/浮点/射线检测几乎不可能跨平台逐位确定，desync 无法根治；③ 命中判定必须服务器权威，且要视野裁剪防透视，而帧同步把所有玩家输入公开、客户端本地算状态，作弊面太大。所以 FPS 用状态同步 + 预测 + 延迟补偿。

</details>

<a id="q15"></a>
<details>
<summary>Q15 逻辑帧与渲染帧有什么区别？</summary>

逻辑帧固定步长（如 20/30/60Hz），执行 `step()` 推进游戏状态，影响结果，必须每端一致；渲染帧由显卡 vsync 决定，频率不固定，只负责把状态画出来（配合帧间插值），不影响逻辑。两者必须解耦，否则「60fps 机器和 144fps 机器跑出不同结果」。

</details>

<a id="q16"></a>
<details>
<summary>Q16 为什么必须固定 tick？</summary>

① 确定性：变步长意味着每帧 `dt` 不同，浮点轨迹不同，「同输入同结果」直接失效；② 回放/校验：回放 = 帧号 + 输入序列，只有步长固定才能复现；③ 物理稳定：固定步长积分器行为可预测，变步长会抖动；④ 网络对齐：帧号是唯一可靠的公共时间轴。

</details>

<a id="q17"></a>
<details>
<summary>Q17 ★ 描述帧同步一帧的完整生命周期（至少 8 步）。</summary>

采集本地输入 → 加输入提前量得到 `target_frame` → 打包（带最近 N 帧冗余）→ UDP 上行 → 服务器按帧号归并（去重策略全端一致）→ 凑齐（或超时托管）标记 ready → 广播该帧完整输入集合 → 客户端入帧缓冲 → 就绪后 `step(f)` → 帧号 +1（可追帧）→ 每 K 帧上报状态哈希 → 服务器影子模拟比对，不一致告警/回灌快照。

</details>

<a id="q18"></a>
<details>
<summary>Q18 输入包为什么必须带帧号，而不是靠到达顺序？</summary>

因为 UDP 会乱序、丢包、重发，到达顺序与逻辑顺序无关；靠顺序推断会把输入写到错误的帧上。帧号让接收方可以「按帧号插入缓冲、按帧号去重、按帧号判定迟到」，也是冗余帧去重与「已执行帧的迟到输入直接丢弃」的基础。

</details>

<a id="q19"></a>
<details>
<summary>Q19 ★ 帧同步卡顿怎么归因？</summary>

分五类：① 频繁小停顿（<100ms）= 某玩家上行抖动大/输入晚到 → 增大提前量、冗余帧；② 长停顿后快进 = 丢包/断线触发超时 → 托管兜底；③ 只有某玩家卡 = 他的链路或算得慢；④ 所有人周期性卡 = 服务器归并/房间主循环抖动 → 查服务端；⑤ 不卡但瞬移 = 单次追帧过多 → 限制追帧并分帧补。

</details>

<a id="q20"></a>
<details>
<summary>Q20 ★ 怎么验证确定性？</summary>

逐帧状态哈希：每 K 帧对关键模拟状态做稳定哈希（FNV-1a/xxHash），序列化顺序固定（按实体 ID 排序）、只用整数、不碰 padding/指针/容器遍历顺序；客户端上报，服务器影子模拟比对。再加开发期断言（无 NaN、坐标范围、实体数上限）与故障期完整状态上传。第一个不一致的帧号就是分叉点。

</details>

<a id="q21"></a>
<details>
<summary>Q21 ★ desync 怎么排查？按什么顺序？</summary>

① 用哈希上报定位第一个不一致帧 `f*`；② 用服务器记录的输入序列本地重放，能复现 = 模拟问题，不能复现 = 输入归并问题（更常见）；③ 逐字节 diff 分叉帧前后的输入集合（托管、补发顺序、重复覆盖策略、帧号偏移）；④ 输入一致仍分叉就二分状态/消融子系统（物理/AI/随机）；⑤ 平台差异（libm、denormal、编译器选项、未初始化内存，用 ASan/MSan/UBSan）；⑥ 定位后加回归用例。

</details>

<a id="q22"></a>
<details>
<summary>Q22 容器遍历顺序为什么会影响确定性？</summary>

模拟里「按什么顺序更新实体/结算伤害」会改变结果（先打谁、谁先死）。哈希表/字典/无序集合的遍历顺序取决于哈希种子与插入历史，不同机器/不同网络到达顺序会不同；不稳定排序对相等元素顺序不保证。对策：用有序容器，或迭代前按唯一 ID 排序；排序键包含唯一 ID；绝不拿指针地址参与逻辑。

</details>

<a id="q23"></a>
<details>
<summary>Q23 ★ 确定性随机怎么实现？</summary>

用显式状态的整数 PRNG（LCG / PCG32 / xorshift），种子由服务器生成并广播；同种子 + 同消耗顺序 → 同序列。三条纪律：内部全用无符号整数（有符号溢出是 UB）；随机数消耗顺序必须与逻辑顺序一致；不要用时间/指针做种子。更稳的做法是**按（种子, 帧号, 实体 ID, 用途）派生**的哈希随机，避免一次多掷/少掷污染后续序列。

</details>

<a id="q24"></a>
<details>
<summary>Q24 确定性三角函数怎么做？精度够吗？</summary>

三种：查表（精度 = 表分辨率）、查表 + 线性插值、CORDIC（只用移位/加减，迭代 N 次约 N bit 精度）。角度用「二进制角」（一圈 = 2^16 或 2^32 份的整数），不用弧度浮点。误差推导：线性插值最大误差约 `(Δθ)²/8`，N=4096 时约 `2.9×10⁻⁷`，远小于 Q16.16 的分辨率 `1.5×10⁻⁵`——所以查表 + 插值对 Q16.16 已经足够，瓶颈是量化本身。

</details>

<a id="q25"></a>
<details>
<summary>Q25 物理引擎跨平台确定性为什么难？</summary>

物理是浮点密集 + 迭代求解 + 容器遍历的组合：宽相遍历顺序影响「先处理哪对碰撞」、窄相接触点/法线在退化情况下不稳定、约束求解对浮点极敏感、积分器怕累积误差、休眠阈值比较受浮点噪声影响、多线程归约顺序不固定。对策只有三条：自研定点物理、锁定同平台同版本、或物理走状态同步（混合方案）。

</details>

<a id="q26"></a>
<details>
<summary>Q26 ★ 描述状态同步的完整时序。</summary>

客户端上报输入（带 seq）→ 服务器校验（CD/资源/距离/频率）→ 入队到 tick t → 服务器 tick 应用输入、模拟、判命中 → 生成快照（含 `last_acked_input`）→ 对每个客户端按 AOI 过滤、按 baseline 做 delta、编码下发 → 客户端收到快照：丢弃已确认输入、用权威状态覆盖、重演 pending 输入、误差平滑 → 渲染（插值时渲染时间落后 100–200ms）。

</details>

<a id="q27"></a>
<details>
<summary>Q27 ★ 收到快照后为什么要「重演」未确认输入？</summary>

因为服务器快照只反映「已确认的输入」，而客户端在等待期间已经预测了更多输入。如果直接用快照覆盖，玩家会被拉回过去的位置，形成每帧回拉的橡皮筋。正确做法：`local = snapshot` 后用 `pending inputs`（seq > ack）按固定 tick 重演一遍，让本地状态回到「服务器状态 + 我的最新预测」，再做视觉平滑。

</details>

<a id="q28"></a>
<details>
<summary>Q28 误差平滑有哪几种策略？</summary>

三种：瞬移（误差超阈值/被击退/传送时直接 snap，诚实但跳）、平滑/混合（50–200ms 内插值到真值，几乎无感）、速度修正（把误差折算成附加速度逐步抵消，最自然但收敛慢）。位置误差与速度误差要分开处理；对穿墙/掉图这类不可接受误差必须直接 snap。

</details>

<a id="q29"></a>
<details>
<summary>Q29 ★ 插值渲染延迟 100–200ms 是怎么来的？</summary>

为了让插值永远有「下一份快照」，渲染时间必须落后至少一份快照间隔，再加网络抖动余量：`D ≥ T_snap + jitter`。20Hz 快照（50ms）+ ±30ms 抖动再留一份余量 ≈ 100–150ms；若快照率只有 10Hz，D 自然升到 150–250ms。这也解释了为什么高竞技 FPS 要提快照率：快照率翻倍，插值延迟能砍掉约一半。

</details>

<a id="q30"></a>
<details>
<summary>Q30 ★ 外推是什么？为什么会「橡皮筋」？</summary>

外推是渲染时间超过最新快照时，按最后已知速度/角速度继续推演（否则画面冻结）。猜错就会橡皮筋：玩家撞墙时外推把角色推进墙，下一份权威快照又把它拉回来。缓解：只对匀速直线运动外推、设置最大外推时间（如 150ms）后冻结、用服务器下发的局部碰撞信息约束外推，或干脆「减速到停」等下一份快照。

</details>

### 16.3 常见卡点与突破方法

| 卡点 | 原因 | 突破方法 |
|---|---|---|
| 「确定性」听起来玄学 | 没有亲手制造过一次 desync | 用 `--desync-at` 亲手复现，再用哈希二分定位 |
| 定点数算不清 | 只在纸上推 | 写 20 行 Python 实现 + 单测，跑一遍溢出用例 |
| 快照/增量概念混淆 | 没区分「相对 baseline」与「相对上一帧」 | 画两条时间轴，标出 baseline 与 delta 链 |
| 预测校正绕 | 一次看太多概念 | 先只做「预测移动 + 收快照重演」，不做平滑和外推 |
| 选型纠结 | 想找「最优解」 | 记住：选型是「你更怕什么」，不是「谁更强」 |

<a id="appendix-b"></a>
## 附录 B：常见误区 15 条

> 这些说法的共同点是「听起来对、细想差一层」。面试里纠正它们，比背定义更能体现深度。

| # | 误区 | 纠正 |
|---|---|---|
| 1 | 「帧同步不需要服务器」 | 生产环境几乎必有服务器：输入归并、补发、回放校验、断线快照。它不模拟世界，但没有它上不了线 |
| 2 | 「状态同步就是全量广播」 | 主流是「脏标记 + 相对 baseline 的增量 + 超限全量兜底」；全量只是最简单的起点 |
| 3 | 「用了 UDP 就不用管可靠性」 | UDP 只是不替你保证；帧同步要自己补输入，状态同步要自己处理丢包后的 baseline 推进与重连 |
| 4 | 「帧同步没有延迟」 | 帧同步的输入延迟往往比状态同步+预测更大（等帧 + 提前量），它的优势是一致性与带宽 |
| 5 | 「浮点天生不确定」 | IEEE 754 基本运算确定；问题在超越函数、编译器重排/FMA、x87 扩展精度、跨架构、未初始化内存 |
| 6 | 「用 double 就能保证确定性」 | 精度更高不解决 libm/编译器/架构差异；反而更慢。要的是可控运算，不是更高精度 |
| 7 | 「定点数就是乘以 1000 取整」 | 那是十进制定点；Q 格式是二进制定点，乘除要移位，溢出要专门分析 |
| 8 | 「状态哈希不一致就是作弊」 | 也可能是版本不一致、未初始化内存、容器遍历顺序、编译器差异；先按 4.11 排查再谈作弊 |
| 9 | 「预测就是让客户端自己算，等于放权」 | 预测只影响表现，最终状态仍以服务器为准；命中/伤害/资产必须服务器裁决 |
| 10 | 「插值延迟越低越好」 | 延迟低于「快照间隔 + 抖动」，插值就没有下一份样本，会频繁外推/卡顿；延迟是买平滑的钱 |
| 11 | 「外推能完全消除卡顿」 | 外推会猜错，猜错就橡皮筋；只对可预测运动外推，并设最大外推时间 |
| 12 | 「延迟补偿是作弊」 | 它是重新分配公平性的机制；但窗口过大确实会成为 lag switch 的利用点，要限幅 |
| 13 | 「Rollback 能用在任何游戏」 | 它要求状态小、可快照、模拟快；大世界/重物理的游戏回滚成本会爆炸 |
| 14 | 「回放就是把状态录下来」 | 帧同步回放 = 输入序列（KB 级）；状态同步才需要录状态/事件（MB 级）。二者成本差两个数量级 |
| 15 | 「选型选最强的那个」 | 选型是「你更怕什么」：怕带宽选帧同步，怕作弊选状态同步，两个都怕就混合 + 付两套成本 |

### C.3 读资料的三个建议

1. **带着问题读**：先有「我想知道插值延迟怎么定」「我想知道回滚窗口多大」这样的问题，再去读，否则会陷进术语。
